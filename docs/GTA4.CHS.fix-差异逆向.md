## 0. 结论先行

**一句话**：fix 版和旧版是**同一套框架、同一批 hook 点**的两次构建，真正的差异不在「字体层」，而在①个别模块补了几条特征码、②新增了版本分桶/指令缓存刷新/NOP 安装器/TLS 上下文等机制、③`whm_table.dat` 根本不是宽度表。

**你给的三条线索，实测两条不成立、一条口径错**：

| 线索 | 实测裁决 | 证据 |
|---|---|---|
| 「模块从 5 个变成 9 个」 | **不成立**。旧版二进制里同样含全部 9 个模块的 `register_patches@<模块>@` 符号；旧版 init `0x1000C700` 对 9 个注册组做静态 `E8` 直调，9 组均在 `[实测确证]` | 我自扫符号 + capstone 反汇编旧版 init：`0xC7F4` benchmark、`0xC7FD` font、`0xC806` game、`0xC80F` html、`0xC818` mail_reply、`0xC821` menu、`0xC82A` phone、`0xC833` save、`0xC83C` whm |
| 「`gta_whm` 是新增模块」 | **不成立**。两版同特征码 `8B AB D8 00 00 00`、同一命中点 `0x5D608D`（我在 exe 可执行节里全局搜索，**唯一命中**）`[实测确证]` | 见 §3.1 |
| 「`gta_mail_reply` 旧 9 → fix 12」 | **不成立**。两版 RTTI 闭包均 11 个（fix 索引 2–12，去重 11）`[实测确证]` | RTTI 三路交叉计数 |
| 「旧版 29 条特征码」 | **口径错**。29 是早期 Ghidra 只重建出 5 个模块时留下的**部分子集**（地址窗 `0x100276E0–0x10028448`），不对应任何现行干净口径。现行口径：pattern 描述符 **旧 62 / fix 67**、RTTI lambda **62 / 62**、asi 侧安装调用点 **旧 60（57 `E8` + 3 `E9`）** | 见 §6.1 |

**Q1 的答案**：14 条字体 hook 在**两版里是同一批**——13 个 `E9` 落点 + 3 个指针捕获，全部 exe 目标 VA 逐条一致、签名逐字节一致；`目标地址改变 / 新增 / 弃用 = 0`。**fix 没有在 `0x91C7C0` 吐正确的 X 轴宽度**：它对这个地址依旧只做「指针捕获」写槽，既不写 `E9`、也没有任何 handler、更没有任何 `Hv/Wv` 除法。

**对我们方案的影响**：fix **不能证伪也不能加强** P4 的「`StubCw` 返回值乘 `Hv/Wv`」；但 fix 给出一条**可以立刻结案**的硬证据：`E8` 站点写 `E8` 而非 `E9`（P4 文档 §8-1 那条「未确证」可以关了）。详见 §7。

### 2.1 专节：`0x91C7C0` 在两版中的处置（Q1 的核心）

**引擎侧事实**（exe 自反汇编复核 `[实测确证]`）：`0x91C7C0` 是测宽本体，`__cdecl` 2 参，结果走 FPU `ST(0)`；前 6 字节 `8A 0D C1 66 03 01` 恰为一条完整指令（余字节 `0F B6 D1 8B C2 69 C0 96 00 00`，我本轮再取一次确认一致）。

旧版封装（我本轮 capstone 实读）：

```
0x10008050  mov eax,[esp+4] / mov eax,[eax] / mov eax,[eax]
0x10008058  mov [0x10037B14],eax / ret 4
```

fix 封装（我本轮 capstone 实读，**多了一个 `ebp` 帧，逻辑一字不差**）：

```
0x10008460  push ebp / mov ebp,esp / mov eax,[ebp+8]
0x10008466  mov eax,[eax] / mov eax,[eax]
0x1000846A  mov [0x10040B34],eax / pop ebp / ret 4
```

**判定**`[实测确证]`：
1. fix **没有**在 `0x91C7C0` 安装 `E9`；**没有**第二条签名命中该地址；**没有任何** handler 在此执行宽度计算。
2. 两版 `.text`/`.data` 对 `0x91C7C0`、视口宽 `0x105C884`、视口高 `0x105C880`、`0x10366A4/A8` 的**静态直接引用数均为 0**——引擎地址全靠运行期特征扫描回填。
3. 因此 **fix 也没有算出正确的 X 轴宽度**。正确式仍是 `W = H · 视口高 / 视口宽`（1920×1080：`0.01573889 × 0.5625 = 0.0088530` ≈ 17.0 px；裸返回 H 则 `0.01573889 × 1920 = 30.22` px，过宽 1.7778 倍）。两版在 `0x91C7C0` 层**都没有**这步乘法。

### 2.2 顺带钉死一处我方旧文档的疑点（`0x60A0` vs `0x6660`）

旧版 W5/W6 的 handler 就是 **`0x60A0`**（我本轮实读：`push esi; mov esi,[esp+8]; movzx eax,si; add eax,0x20; call 0x1D50(iswprint); …; mov ecx,0x10037AD8; push esi; call 0x6B00; ret`）。`0x6660` 是**另一个函数**——自绘 quad 的画字 handler（入口 `sub esp,0x2C` + 栈 cookie + `[0x10037AF8]` 状态对象）。两者不冲突：`0x6660` 由另一处封装 `0x78C0`/槽 `0x10035318` 转入（属绘制层，不属 `gta_font` 的宽度条目）。**此前「文档记 `0x60A0` 与自反汇编 `0x6660` 有出入」是因为把绘制 thunk 误读成了 W6。**

### 3.2 `whm_table.dat` 的真实格式（我独立复核，非转述）

对 `release\plugins\GTA4.CHS\whm_table.dat`（780,676 B）逐字节解析 `[实测确证]`：

| 项 | 值 |
|---|---|
| 头 | u32 `N = 5388` |
| 条目区 | 5388 × (`u32 key`, `u32 offset`)，`4 + 8*5388 = 43,108` 字节起为串块 |
| 串块 | 737,568 B；**首 4 字节 `1C 41 0B 00` = 0x000B411C = 737,564**（块内载荷长度），其后 NUL 分隔 UTF-8 串 |
| 偏移 | 升序、唯一（`sorted=True`, `unique=5388`），最大值 737,437 落在串块内 |
| `key` | 有重复（`unique_keys=False`）→ 哈希键而非索引 |
| 内容 | 串块含 **211,686 个汉字**、5389 个 NUL；抽样：`男` / `文化评论员` / `三流白人男性` / `爱好:写博客…` / `自由城，` / `Alderney市，` / `我们不碰可卡因和冰毒…` |
| 是否浮点宽度 | 头 5000 个 key 里仅 189 个能被解释成 (0,1) 区间 float（≈随机命中率）→ **否** |

**结论**：这是「**英文原文（FNV 哈希）→ 中文译文偏移**」的短语替换表。名字里的 `whm` 更像 **word/string hash map**，与「width/height metrics」无关。`[实测确证]`（`key` 具体是哪一轮 FNV、英文源串不在表内故无法离线对账 → `[未确证]`，`[强推断]` 为英文原文 FNV-1a）

### 3.3 那宽度数组到底是谁的？

**仍是引擎自己的**，两版都只是把它「捕获出来」`[实测确证]`：

- fix 侧宽度基址 `0x10040B10`（旧版 `0x10037AF0`），第二段 `+0x960`（`0x10040B14` / 旧 `0x10037B04`）保留；
- 只由捕获桩（fix `0x10008690` 等）经对象链 `[arg]→[eax]→[eax]→[eax+4]` 从引擎对象解引用取得；
- **没有任何指令同时引用 whm 全局与宽度全局**，即不存在把 whm 块 memcpy 进宽度区域的代码；
- 宽度公式保留（`0x10006040` / `0x100060C0` / `0x10006190`），只是把旧版硬编码常量（`0x96` 步长、数组基址、除数）改成运行期全局。

> 所以旧版文档里「`whm_table.dat` 格式未解码、可能是宽度主来源」的悬案，到这里**结案：它不是宽度表**。

## 5. Q4：版本 / locale 检测

### 5.1 版本检测 `0x1001CF50` `[实测确证]`

- 先走 VersionInfo：`GetFileVersionInfoSizeW` → `GetFileVersionInfoW` → `VerQueryValueW`（子块根 `"\"`，串 @ `0x10031814`，取 `VS_FIXEDFILEINFO`：`0x08 = dwFileVersionMS`、`0x0C = dwFileVersionLS`）。
- 分桶：`minor == 0` 时按某字段 `ecx` 取 `4→桶0`、`7→桶1`、`8→桶2`，其余转体积路径；`minor == 2 → 桶3`；**都不匹配 → 桶4**。
- 资源版本 ↔ 桶：`1.0.4.x→0`、`1.0.7.x→1`、`1.0.8.x→2`、`1.2.0.x→3`（`[强推断]`，以代码偏移为准）。
- **兜底走体积指纹**（`GetFileAttributesExW` 取体积，表 `0x100317F0`、标志字节表 `0x10031810`）：**桶3 阈值 `17,425,752` B ＝ 本机目标 exe 的实测体积，双路吻合** `[实测确证]`。
- 消费 `0x1000D2A0`：`al = 桶号` → 桶0 全量初始化；桶1/2 走 `0x1001D430(布尔)`；桶3 用固定 handler 表（`0x10007A10…0x1000CD20`）；桶4 无正向支持，特征码不命中就**静默跳过**。

### 5.2 locale `[实测确证] + [强推断]`

`GetLocaleInfoEx` / `LCIDToLocaleName` / `LCMapStringEx` 的调用点全在 **CRT 初始化区**（默认 LCID `0x409`），**不是补丁级语言门控**。静态未见「仅特定语言才启用」「按 locale 选字体」的证据。

### 5.3 能不能跑在别的版本上

- `[强推断]` fix 为 4 个版本桶各备一套轮廓（1.0.4 / 1.0.7 / 1.0.8 / 1.2.0.x）；目标 1.2.0.59 落桶3（版本号与体积双路吻合）。桶0/1/2 是否各自带**完整可用**特征码，静态只见桶3 的固定 handler 表 → `[未确证]`。
- 旧版**没有** VERSION.dll、没有版本分支，全部特征码只针对 1.2.0.59，不命中即跳过。
- 实践结论：**桶4（版本/体积都不匹配）等于不生效**；想换版本必须命中对应桶，且桶0–2 的有效性未验。

**我们该不该学**：`[建议]` 值得学「**版本/体积双指纹 + 不匹配就静默跳过**」这个保守策略（我们现在只有「签名 count==1 + 原字节校验 + 拒装」，其实等价甚至更严）；**不建议**引入 VERSION.dll 硬依赖——我们的目标是单一 exe 版本，多一层依赖只增加失败面。

### 6.3 关键结论：**`E8` 站点写 `E8`，不是 `E9`**

这条直接结掉 P4 文档 §8-1 的未确证项：安装器 A（对应 `E8` call 站点，如 W5/W6/W11）写的是 **`0xE8`**，因此被 hook 的函数**仍以 call 语义进入**、handler 的 `ret` 有返回地址可弹；只有非 call 站点（W1/W9/W10 等）才由安装器 B 写 `0xE9` + 自带 resume。**旧补丁表格里那些「统一记 `E9`」的字节列不能照抄。**

### 6.4 另外三项机制变化

- **TLS**：`TlsAlloc/Get/Set/Free`（`0x10021230`）保存**每线程 `0x2888` B 上下文**，用于翻译/补丁状态，**不是 hook 分发**。`[实测确证]`
- **ASLR**：`GetModuleHandleW(NULL)` 取基址 + PE 头解析；**代码指令流中无 `0x400000` 立即数**（117 个 dword 均在编码数据/哈希表）。两版都 ASLR 安全，目标 = 运行期基址 + 命中偏移。`[实测确证]`
- **`Could not parse pattern.`**：特征码解析器保留并带错误提示——说明匹配器有完整文法（支持 `?` 通配与位移修饰），这也是 fix 唯一命中数能从 33 涨到 56 的原因之一。

## 7. 对我们 P4 落地方案的影响（**要不要改**）

先给结论表：

| P4 里的结论 | fix 版的作用 | 判定 |
|---|---|---|
| 「`StubCw` 返回裸 H，少除一个 `Hv/Wv`，应改为 `H·Hv/Wv`」 | fix 在 `0x91C7C0` **什么都没做**（纯捕获） | **既未证伪，也未加强**（fix 走的是另一条路） |
| 「只改 W 槽会重叠，必须改 `0x91C7C0` 这个共同源」 | fix 的 W5/W6 正装在 `0x92197E`（字距）与 `0x92381E`，说明「字距必须单独管住」这个判断是对的 | **加强（机理层面）** |
| 「`E8` 站点写 `E8` 还是 `E9` 未确证」（P4 §8-1） | fix 安装器 A 明确写 `0xE8` | **可结案：写 `E8`** |
| 「我们的方案需要真机验证宽度」 | fix 的做法是**自绘 + 自有表**，它的正确性不来自引擎宽度 | **不变：仍需我们自己跑一次** |

### 7.1 为什么 fix 既不能证伪也不能加强

fix 把「宽度正确」这件事**绕开了**，不是解决了：它的做法是接管单字宽（W4）→ 接管两条前进量（W5/W6）→ 接管整串测宽（W2/W3）→ 再用自己的 whm 表算 advance + 自绘 quad（`0x6660`）。它**从不依赖引擎算出正确的 X 轴宽度**。

我们的做法（复用引擎的四边形路径）恰恰**必须**依赖引擎宽度正确，所以在 `0x91C7C0` 源头补 `Hv/Wv` 是必要且充分的——**这条路 fix 根本没走，所以它的存在既不能证明我们错、也不能替我们验对**。

### 7.2 反而更强的一条论证：我们比它省

fix/旧版这条路要覆盖 **13 个 `E9` 落点 + 3 个捕获 + 一套自绘 handler + 一张自有宽度表**；我们只要**一个返回值**（`0x91C7C0` 命中分支 `fld` 一个校正值）就能让 14 处调用点（几何宽、字距、整行测宽/换行、守卫、回退）全部自动一致。这不是「更聪明」，而是**选择在共同源头上修**带来的结构优势。旧补丁必须散装 13 个点，是因为它同时要换测量、换前进量、换绘制——它无法只修一处。

### 7.3 明确要改 / 不要改

**要改（但改动很小，且已在 P4 文档内）**：
1. `P4-hook-落地方案(REA逆向).md` §8-1「`E8` 站点写 `E8` 还是 `E9`」→ **结案为「写 `E8`」**。这是一句状态更新，不是方案变更。
2. `§2.2` 那张表标题写的「12 行」→ 实为 **13 个 `E9` 落点**（W4、W11 各双命中）。条目标题需更正，表内数据本身无误。
3. `whm_table.dat` 相关表述：P4 文档只把它当「旧补丁宽度来源的未解码悬案」——现在可以写死「**它不是宽度表，是短语替换哈希表**」，旧补丁的宽度来自引擎对象数组 + ASI 自有特表。

**不要改（fix 版没有提供更正确的宽度做法）**：
- 不改 `W = H·Hv/Wv` 这个算式，不改「在 `0x91C7C0` 命中分支返回」这个位置；
- 不引入 fix 的自绘 quad 路线（`0x6660` + 自有表）——那是把 1 个返回值换成一条链，且要改 64×66 格子参数；
- 不引入 VERSION.dll 版本分桶（我们只针对 1.2.0.59）；
- 不引入 TLS 每线程上下文（我们无跨线程状态）；
- `FlushInstructionCache` **我们已有**（`font.cpp:358`（trampoline）/`368`（站点）/`449`），不必再补；
- 固定 6 字节覆盖 **不必**改成 fix 那种序言扫描器（`0x91C7C0` 前 6 字节恰为完整指令，fix 的自适应器是为「覆盖长度不定」的站点准备的）。

### 7.4 唯一值得抄的一条（与宽度无关）

若将来要做「全中文」而不只是「汉字能看」，需要补 §4 里那几类运行期文本。fix 的 `whm` 范式（FNV 键表 + 文本缓冲钩子）可以直接借鉴——**这是一个新议题，不属于当前 P4 宽度层**。
