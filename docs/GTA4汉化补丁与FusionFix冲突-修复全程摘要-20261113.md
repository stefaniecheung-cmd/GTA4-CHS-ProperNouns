## 1. 术语与记号（非逆向背景可直接跳过，遇到再看）



| 记号 / 术语        | 含义                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------- |
| RVA            | Relative Virtual Address，相对模块（此处指 `GTAIV.exe`）基址的偏移。本文所有 "地址" 除标注 "文件偏移" 外均为 RVA              |
| 文件偏移 (fo)      | `.asi` / `.exe` 文件里从 0 开始的字节位置，与 RVA 差在节对齐                                                    |
| 基址             | 模块被加载到的内存起点；CE 版 `GTAIV.exe` 实测 `0x00470000`，`GTA4.CHS.asi` 实测 `0x517D0000`                   |
| `byte_pattern` | 中文包使用的特征码扫描库（源自 ThirteenAG 的 Hooking.Patterns），按字节签名在内存里搜索目标指令                                |
| `aslr_ptr`     | 中文包依赖的 injector 里的辅助函数，作用是 " 把按默认基址 `0x400000` 写的地址换算成当前实际基址 "——**它无条件加位移，不判断传入的地址是否已经是实际地址** |
| hook           | 在目标指令处写入跳转，把执行流引到自己代码，事后再跳回                                                                   |
| `CALL rel32`   | x86 5 字节相对调用；`E8` + 4 字节有符号位移，位移按 "下一条指令地址" 计算                                                |
| 写 AV           | Access Violation，`0xC0000005` 且 `ExceptionInformation[0]=1` 表示写访问越界 / 不可写                     |

## 2. 现象与起点

同一套装（FusionFix + 中文包）下出现三个症状：



1. 暂停菜单**随机卡死**—— 不是崩溃、不是驱动重置；完整转储里是 111 线程、渲染线程真挂起。

2. 暂停菜单底部**整片黄色&#x20;**`?`（约 5–6 行 × 40–60 列），但**菜单项名是正常中文** ⇒ 中文包本身工作正常，出问题的是 "被额外注入的那段文本"。

3. 另有**必然闪退**：`Code=0xC0000005`、`ExceptionAddress=0x006B9B5F`（RVA `0x249B5F`）、`NumberParameters=2`、`Info[0]=1`（写）、`Info[1]=0x74C08501`。

**关键对照实验**：把 `GTA4.CHS.asi` 改名 `.off` 后 ——



* `?` 墙**完全消失**，但出现大量 `!!!!` 竖向占位块 ⇒ `?` 墙由中文包参与渲染链导致；同时排除了 "缺字形" 的粗糙解释（缺字形显示 `!`，查表失败才显示 `?`）。

* 同一套装在 \*\* 桌面（7900XT）与掌机（Legion Go S）\*\* 两台独立机器上均复现 ⇒ 与硬件无关；关 DLSS、换不换 DXVK 均复现。

## 3. 线 A：文本路径（`?` 墙 + 挂起）

### 3.1 机制

FusionFix 的 `[MISC] ExtraInfo = 1` 会在**运行期自己拼一段附加文本**（`~p~IMG Files:`、`~r~WARNING: …`），塞进暂停菜单底部。这段文本是**纯 ASCII**。

中文包 `GTA4.CHS.asi`（ImageBase `0x10000000`）把这套游戏的文本排版路径整体接管了：



| 函数                        | RVA             | 说明                                                                                                              |
| ------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------- |
| `GetStringWidthRemake`    | `0x62E0`        | 排版入口；`0x6362` 调 `GetString`                                                                                     |
| `CStringTable::GetString` | `0x15A50`       | `0x15A75` 调 `hash_string` 查表                                                                                    |
| `hash_string`             | `0x2370`        | FNV 变体；`0x2381 cmp eax,0x1000` / `0x2386 jae` ⇒ **算长上限 4096**；主循环 `0x23A2…0x23C6` 每步 `inc edx`、**不检查 NUL 提前退出** |
| 排版循环                      | `0x6380…0x646B` | `movzx esi,word[edi]` → `call 0x5F70` 发射 → `add edi,2`，`cmp eax,0x1000` 上限                                      |
| `GetMaxWordWidth`         | `0x6240`        | 对**每个词**重调 `0x62E0`，而后者进门又整串哈希 ⇒ **O(N²)**                                                                      |
| `IsNativeChar`            | `0x1E40`        | 仅 ASCII `0x20–0x7E` 算 "原生字形"                                                                                    |

`char_table.dat` 实测：**3,625 条**（14,500 字节，每 4 字节一条），**ASCII&#x20;**`0x20–0x7E`**&#x20;覆盖 = 0 / 95**（其余为 CJK 3,605、全角 9、中文标点 9、`0x2014` 1）。

⇒ 在这条 "被中文包接管后" 的解析链里，ASCII 虽然本来算 "原生字符"，但已经不在字表里 ⇒ 每个字符都回退成 `?`；一段 150 字符的文本按底部宽度换行，正好就是屏幕上那面 `?` 墙。

### 3.2 挂起现场



```
TID 40116 (render thread)
EIP = 0x674B23C6   (= GTA4.CHS.asi + 0x23C6，hash_string 主循环 cmp edx,edi)
ECX = 0x674F0AD8   (字符串表对象)
EDI = 0x368B37C8   = 串首 0x368B17C8 + 0x2000   ← 撞满 4096 宽字符上限
```

`EDI` 停在 " 串首 + `0x2000`"，说明哈希循环吃满 4096 个宽字符仍未遇到 `0x0000` ⇒ 送进来的不是一条正常宽字符串；再叠加 `GetMaxWordWidth` 的 O (N²) 整串重算，渲染线程被摁死在这条链上（挂起而非崩溃）。

### 3.3 处置



* **用户侧立竿见影**：`GTAIV.EFLC.FusionFix.ini` 里 `[MISC] ExtraInfo = 0` → `?` 墙与卡死在同一次改动后同时消失。

* 这与上游 `ThirteenAG/GTAIV.EFLC.FusionFix#1270`（报告者点名 `ExtraInfo`、并确认 `ExtraInfo=0` 修好）以及 `#1663`（duplicate）的定性一致：语言包相当于 "额外新增一种语言"，FusionFix 没为这种情形留处理。

* **根治方向**：


  * FusionFix 侧：`ExtraInfo` 文本不要拼成裸 `std::wstring` 直接交给渲染，改走与原生语言一致的字符串表路径（`GXTLoader`）；或开启前探测当前语言的字形覆盖，不满足就自动跳过或降级为英文原生串。

  * 中文包侧：`font.cpp` 的 token 尾扫描在按 token 处理前先判 `*p == 0`；`hash_string` 撞满 4096 上限时记一条一次性告警（现为静默）；`GetMaxWordWidth` 改为进函数时算一次整串哈希、逐词复用。

## 4. 线 B：代码路径（闪退，真正的硬缺陷）

### 4.1 三份转储完全一致（先排除 "偶发竞态"）



| 项                         | 三份 `.dmp`（合计约 8 GB）取值               |
| ------------------------- | ----------------------------------- |
| `Code`                    | `0xC0000005`                        |
| `ExceptionAddress`        | `0x006B9B5F`（RVA `0x249B5F`）        |
| `ExceptionInformation[0]` | `1`（写访问）                            |
| `ExceptionInformation[1]` | `0x74C08501`                        |
| `GTAIV.exe` 基址            | `0x00470000`                        |
| `GTA4.CHS.asi` 基址         | `0x517D0000`（`SizeOfImage 0x46000`） |

崩溃点内存三份逐字节相同：



```
1C D2 DE FF | 8B 87 E8 65 F4 11 | 51 | 90 90 90 90 | 88 05 01 | 85 C0 74
```

`rel32 = 0x5111F465` → 目标 `0x517D8FC0` = **中文包 +&#x20;**`0x8FC0`（这套补丁自己的 guard 函数）。也就是说：**有人往游戏代码里写了一条跳向中文包&#x20;**`+0x8FC0`**&#x20;的&#x20;**`call`**，但位移算错了，连带把后面 4 字节填成了&#x20;**`NOP`**。**

### 4.2 源码走查（仓库 `https://github.com/QCJW/GTA4.CHS`）



1. 中文包的 hook 引擎就是 ThirteenAG 的 `Hooking.Patterns`（`plugin/byte_pattern.cpp`），`_range.first = module`（该文件 227 行）⇒ **扫描结果天生就是运行时绝对地址**。

2. `plugin/gta_html.cpp` 53–72 行：特征码 `F3 0F 5C 4B 04 0F 2E C1 9F F6 C4 44 7B 27` 命中后取 `a = addresses[0].i(0)`（56 行），`jmp_va = a + 0x33`（58 行），判 `*jmp_va == 0xEB`（60 行），算 `rel`（62–63 行），再调用 `gta_html_link::install_link_rect_fix(a + 5, jmp_va + 2 + rel, 0x27C)`（65–66 行）。

3. `plugin/gta_html_link.cpp` 91–97 行：



```
void install_link_rect_fix(std::uintptr_t hook_va, std::uintptr_t done_va, std::uintptr_t origin_off)
{
    g_origin_off = origin_off;
    g_link_rect_done_va = reinterpret_cast<std::uintptr_t>(injector::aslr_ptr(done_va).get<unsigned char>()); // 94
    injector::MakeCALL(injector::aslr_ptr(hook_va).get(), html_link_rect_guard);                                 // 95
    injector::MakeNOP(injector::aslr_ptr(hook_va + 5).get(), 4);                                                // 96
}
```



1. `aslr_ptr` 是 "**无条件加位移**"：`injector.hpp:726` → `gvm.hpp:202–209`，`fn_mem_translator_aslr::operator()` 返回 `p - (0x400000 - module)`，即 `p + module - 0x400000`。

⇒ 两个**已经绝对化**的地址被再抬一次模块偏置 = **位移加了两遍**。这就是全部根因。

### 4.3 算术闭环



| 项               | 值                                                        |
| --------------- | -------------------------------------------------------- |
| 特征码真实命中         | RVA `0x1D9B51`（磁盘 fo `0x1D8F51`）                         |
| 正确 hook 点 `a+5` | RVA `0x1D9B56`（`ucomiss xmm0,xmm1` 指令起点，合法边界）            |
| 模块偏置            | `0x470000 - 0x400000` = `0x70000`                        |
| 实际被写入地址         | `0x1D9B56 + 0x70000` = **RVA&#x20;**`0x249B56`           |
| 崩点              | `0x249B5F` = 写点 **+9**（`MakeNOP` 的 4 字节正好盖到）             |
| 被破坏的原指令         | `0x249B54` 原为 `8B 87 98 00 00 00`（`mov eax,[edi+0x98]`）  |
| 改写后的位移          | `0x11F465E8` ⇒ 执行流被解码成 `mov byte ptr [0x74C08501], al`   |
| 为何走这条分支         | `[a+0x33]`（RVA `0x1D9B84`）= `EB 23`，确认 `*jmp_va == 0xEB` |
| `done` 地址       | RVA `0x1D9BA9`，同样被抬 `0x70000` ⇒ **两个地址必须一起改**            |

`0x249B54` 处原 6 字节 `8B 87 98 00 00 00` 被 `E8 xx xx xx xx` + `90 90 90 90` 覆盖后，残留的 `88 05 01 85 C0 74` 让 CPU 把 `E8` 的 4 字节位移当成另一条指令的操作数 ⇒ 执行成 `mov byte ptr [0x74C08501], al`，写不可写地址 → `0xC0000005`。这正是转储里 `Info[1]=0x74C08501` 的来历，也是 "三份转储一模一样" 的原因：**每次都是同一处 9 字节被写坏**。

### 4.4 为什么 6 条 hook 只有这一条中招



| hook 点 RVA                                                  | 出处                                  | 写法                                  | 是否走 `aslr_ptr` |
| ----------------------------------------------------------- | ----------------------------------- | ----------------------------------- | -------------- |
| `0x12A7A` / `0x13311` / `0x13523` / `0x1E49DE` / `0x1E4CCE` | `plugin/gta_mail_reply.cpp` 的 `reg` | `MakeInline` + 裸指针                  | 否              |
| `0x1D9B56`（本处）                                              | `plugin/gta_html_link.cpp`          | `MakeCALL` / `MakeNOP` + `aslr_ptr` | **是**（唯一）      |

中文包里 `aslr_ptr` 的内联实现全在 RVA `0x8F50`，**全文件只有 3 个调用点**（`0x901C` / `0x9040` / `0x9065`，都在 `0x9000` 的安装器里），恰好只服务这一条 hook ⇒ 影响面很窄，但一旦触发必然闪退。

### 5.2 本地二进制（不改 `GTAIV.exe`，只动中文包 1 字节）

同一根因在二进制上的等效修法：把 `aslr_ptr` 的内联实现退化成恒等函数。

内联体反汇编（RVA `0x8F50` 起）：



```
0x8F72  mov  ecx,[0x10040a3c]     ; module base
0x8F7B  add  ecx,0xFFC00000       ; 81 C1 00 00 C0 FF  （即 -0x400000）
0x8F81  add  ecx,esi              ; 03 CE              ← 把 p 也加进来
0x8F84  mov  [eax],ecx
0x8F8x  ret  4
```



| 项          | 值                                                         |
| ---------- | --------------------------------------------------------- |
| 改动文件       | `plugins\GTA4.CHS.asi`（269,312 字节，`ImageBase 0x10000000`） |
| 文件偏移       | `0x08381`                                                 |
| 改动         | `03` → `8B`（`add ecx,esi` → `mov ecx,esi`；第二字节 `CE` 两边相同） |
| 实际差异       | **1 字节**（与备份逐字节比对确认，无其他改动）                                |
| SHA-256 前缀 | 原 `2184b3ed178de41e…` → 新 `2eb58176cd47d12c…`             |
| 备份         | `plugins\GTA4.CHS.asi.bak-20261113`（改动前生成）                |
| 回滚         | 用备份覆盖；或把偏移 `0x08381` 改回 `03`                              |
| 前提         | 不修改 `GTAIV.exe`                                           |

改后 `aslr_ptr` 恒等 ⇒ 传入地址原样使用 ⇒ 安装器把 `call` 写回 `0x1D9B56`（正确位置），不再碰 `0x249B54`。

**更激进的备用方案**（该功能整体放弃）：`0x080E0`（RVA `0x8CE0`）是安装器入口，开头为 `55 8B EC 8B 45 08 83 EC`，改成直接 `ret` 即可让这条 hook 完全不安装。

## 7. 已排除的旁支（避免后来者重复踩坑）



| 猜测                            | 结论                                                                        |
| ----------------------------- | ------------------------------------------------------------------------- |
| 数据里有超长串 / 不闭合 `~` token       | 全目录按 NUL 扫描，最长合法串 1,324；6 份 gxt + JSON 中不闭合 `~` 均为 0                      |
| `custom_translations.json` 作祟 | 86 条、含 `~` 0、最长 15，与 4096 无关                                              |
| FusionFix 用硬编码 RVA 打补丁        | 中文包 10 个 hook 目标 RVA 在 FusionFix `.text` 里 dword 命中 **0 处**；它是特征码扫描式 hook |
| `?` 墙由 DXVK / DLSS 引起         | 关 DLSS 仍复现；换不换 DXVK 均复现；桌面 + 掌机双机复现 ⇒ 与硬件无关                               |
| `.asi` 本体损坏或版本不匹配             | SHA-256 与发布一致；改名 `.off` 后症状全部消失                                           |
| Steam 版补丁是 "修好版"              | 证伪（Steam 版连 4096 上限和 NUL 检查都没有）                                           |

## 8. 被推翻的旧结论（方法论留档）



| 旧结论                                | 推翻依据                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------ |
| "hook 落点偏 2 字节，`0x249B5E` 是 `lea`" | 按源码 `a+5` 应为 `0x1D9B56`，实际写到 `0x249B56`—— 差的是**整个模块偏置&#x20;**`0x70000`，不是 2 字节 |
| "`0x249B56` 是某条特征码 + 偏移的落点 "       | 全表套 `GTAIV.exe`（含 ±2/+5/+7/+9/+33）**0 命中**                                     |
| "中文包的 hook 由硬编码 RVA 表驱动"           | 实为 **60 条 ASCII 特征码**驱动                                                        |
| " 某份转储的 `rel = 0x5111F555`"        | 该字段属另一处调用，与本次无关                                                                |

**教训**：只有转储、没有源码时，"落点偏几字节" 这类推断极易把**系统性偏置**误读成**局部错位**。拿到源码后第一件事应当是确认 "地址是绝对的还是相对的"——`byte_pattern` 返回绝对地址这一条，决定了后面所有算术。

## 9. 读者自查 / 复现步骤



1. 确认装的是 **CE 版**中文包（`GTA4.CHS.asi`，269,312 字节）。

2. 查 SHA-256：首 16 位为 `2184b3ed178de41e` = **未打补丁**原版；`2eb58176cd47d12c` = 1 字节补丁后的形态。

3. 复现 `?` 墙：`[MISC] ExtraInfo = 1` + 进「设置 / 显示」页 → 底部出现 5–6 行 `?`；设为 `0` 应立刻消失。

4. 复现闪退：在暂停菜单里点进带超链接的文字区（触发 `install_link_rect_fix` 那条 hook 的锚点），或反复进出菜单直到命中。**崩点固定为&#x20;**`0x249B5F`**、**`ExceptionInformation[1] = 0x74C08501`**—— 只要这两个值对上就是本问题，不必再查显卡 / 驱动。**

5. 不改文件自查：用十六进制工具看 `GTA4.CHS.asi` 偏移 `0x08381`，`03 CE` = 原版，`8B CE` = 已修补。
