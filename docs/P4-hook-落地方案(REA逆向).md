# P4 hook 落地方案（REA 逆向）

> 目标：把旧汉化补丁 `GTA4.CHS.asi` 的**字体宽度层**逆清楚，并给出我方最省事的落地路线。
> 取证目标：`GTAIV.exe` 1.2.0.59（17,425,752 B，ImageBase `0x400000`，`.text` RVA `0x1000`，SHA1 `32A3F889F9FCC572EA798213F2E9EB429EB0C9A3`）、`GTA4.CHS.asi`（232,960 B，ImageBase `0x10000000`，SHA1 `9E91C078704EDE05C34883AA3F694D6914F577A4`）。
> 工具：capstone / pefile 静态反汇编 + 磁盘 PE 字节逐条比对 + 29 条特征码全量静态匹配。
> **本文档是只读分析的产物：未修改游戏目录下任何文件（不含源码以外的写入、含源码也未改）、未启动游戏、未改 `config.ini`、未编译、未部署。**
> 证据等级：**[实测确证]** 本次反汇编/磁盘字节/源码逐行直接读到；**[强推断]** 由已确证链路推出；**[未确证]** 有卡点，需一次运行期验证。

## 0. 一句话结论（先说最重要的纠正）

问题**不是「缺 hook」**。`0x91C7C0`（引擎测宽本体）在现源码里**已经被接管了**（`font.cpp:129-146` 的 `StubCw`，6 字节 `E9` + trampoline）。

缺的是**一个因子**：`StubCw` 命中汉字时直接 `call [g_atCwHeight]` 返回引擎的**字高 H**，而 H 是 **Y 轴**归一化量、宽度是 **X 轴**归一化量，两者差一个 `Hv/Wv`（1920×1080 下 `= 0.5625`）。于是汉字得到 `H*1920 = 30.22 px` 宽、`H*1080 = 16.998 px` 高 —— **正是你看到的「过宽 78%」**。

```
现在（StubCw 返回 H）        →  30.22 × 16.998 px，间距 30.22
应该（StubCw 返回 H·Hv/Wv）  →  17.00 × 16.998 px，间距 17.00
```

**落地动作 = 在 `StubCw` 里把返回值从 `H` 改成 `H × Hv/Wv`，两条指令级别；不需要新增 hook、不需要自绘。**

## 1. 引擎侧读数：为什么是 3.1186 / 30.22

### 1.1 两组实测值的来源（务必分清）

| 场景 | 汉字四边形 | 汉字 pen 步距 | 说明 |
|---|---|---|---|
| 引擎原样（未接管 `0x91C7C0`） | 3.1186 px 宽 × 16.998 px 高 | 3.1186 px | 宽度表项本身偏小（不是单位错） |
| 现源码 `StubCw` 返回 H | **30.22 px 宽 × 16.998 px 高** | 30.22 px | H 当宽度用了，多了一个 `1.7779 = 1920/1080` |

反推自洽性：`W_norm = 0.00162427`、`H_norm = 0.01573888`，`Δy/Δx = 5.4505 = 0.5625 × 9.6898`（前者是 `Hv/Wv`，后者是 `H/W`）。UV 侧完全正确（`ΔU = ΔV = 32/4096 = 0.0078125`，`u_left = col*32/4096` 与 `idx = row*128 + col` 严丝合缝），`bq == vx == sdN`，排除「没画 / 整批丢弃」。

> 本机 `commandline.txt` 为 `-width 1920 -height 1080 -windowed`；实测过宽倍数 `30.22/16.998 = 1.7779` 正是 16:9。代码与现象互证。

### 1.2 单位：视口归一化，X 乘视口宽、Y 乘视口高 [实测确证]

- 测宽 `0x91C7C0` 完整链：`[esp+8]` 取字符 → `mov cl,[0x10366C1]`（font）→ `[0x10366BD]`（mode）→ `(font + 3*mode)*256*2` 定位映射表 `0x1193C78`（768 word/字体）→ 槽号（`*0x258`）→ `fontRec` 首字节前进宽度 `[rec+slot*0x258+ch]` → `+ 页UV基值(0x119567C, 150 项/页)` → `/ [0x1036690]` → `+ [0x10366C4]` → `× [0x10366A4]`，**结果以 FPU `ST(0)` 返回**；`ch<0x100` 直接跳过查表；`[0x1036690]==0` 时跳过除法。
- 测高 `0x91C7A0`：`H = [0x10366A8] × 0.065580`（常量在 `0xE85F6C`），不读字符、无副作用，`ST(0)` 返回。
- **像素化只发生在 `0x91B850`（组四边形）**：归一化坐标 × 缓存的后缓冲像素尺寸（宽 `0x105C884` / 高 `0x105C880`）。`0x90A360` 只拷顶点（36 B/顶点，缓冲 `0x1195F70`，游标 `0x1195EA0[font*4]`，满 170 提交），`0x8D4340` 提交无任何坐标乘法。

### 1.3 唯一正确的宽度式

```
W' = H · Hv / Wv
  H   = [0x10366A8] × 0.065580           （即 0x91C7A0 的返回值，Y 轴归一化）
  Hv  = [0x105C880]（主线程槽 [0x105C87C]；原始源 0x17ED8D4）
  Wv  = [0x105C884]（主线程槽 [0x105C888]；原始源 0x17ED8CC）
  兜底：Wv/Hv 为 0 或未初始化 → 800×600（比值 0.75）
```

- 1920×1080：`0.01573888 × 0.5625 = 0.00885312` → 像素宽 `17.00`，与高相等（正方形格）✓
- **非 16:9 必须用运行时 `Hv/Wv`**：16:10 是 0.625，4:3 是 0.75。写死 0.5625 会在这些分辨率下偏窄。
- 视口来源（实测）：`WM_SIZE` → `0x17ED8CC`(宽)/`0x17ED8D4`(高) → 缓存 `0x105C884/888` / `0x105C880/87C`；引擎自己在 `0x9237C8` 用 `884/888 ÷ 880/87C` 算宽高比，**反证轴归属正确**。

### 1.4 字距与四边形同源 —— 所以用一个返回值就能双修 [实测确证]

- `0x921140`（逐字绘制）是 **void 返回**：出口 `0x9217F2 pop edi; pop esi; add esp,0x30; ret`，不回传 EAX，三个调用方都不接。
- 块渲染循环在 `0x921976 call 0x921140` 画完字后，**另起一次** `0x92197E call 0x91C7C0` 取前进量：`0x921983 fstp` → `0x92198D addss xmm0,[ebx]` → `0x92199D movss [ebx],xmm0` 推进 pen x。
- 两者的**唯一共同来源就是 `0x91C7C0` 的返回值**。因此：
  - 只改 W 槽 `A+0x24` → 四边形变宽、**pen 仍按原值走 → 汉字重叠**（这是「为什么不能只写栈槽」的硬证据）；
  - 改 `0x91C7C0` 的返回 → 四边形、字距、整行测宽/换行**一次全对**。

`0x91C7C0` 的 14 处调用点分类：

| 地址 | 用途 | 类别 |
|---|---|---|
| `0x921537` | 路径 B 四边形宽度（唯一进 W 槽 `A+0x24`） | **逐字绘制几何** |
| `0x92197E` | 块渲染逐字 pen 前进量 | **字距推进** |
| `0x921185` | 入口边界/溢出守卫（`÷A4` 后 `comiss` 限幅，超限不画） | 守卫 |
| `0x9211EF` / `0x92121C` / `0x921872` / `0x921892` / `0x9219D0` / `0x921A09` | `0xFD` / `0xFFFF` 回退码前进量 | 回退 |
| `0x9235D7` / `0x9235FB` / `0x923778` / `0x92380A` / `0x92381E` | 布局 pass 整行测宽/换行 | 整行测宽 |

### 1.6 三处旧口径必须纠正（别再把它们写进方案）

1. **`dl == 0` 门在当前部署件里不存在**。它是更早一版 stub 里的东西；扫引擎 `.text` 找 `cmp dl,0` 得 0 命中是方法错了。引擎侧唯一字体比较是 `0x92114C` `80 3D C1 66 03 01 03`（font==3 早退），路径 B 条件是 font==2。
2. **度量常量偏移**：`+0x24C`(40.0)、`+0x250`(4.0)、`+0x254`(39.5)，U 除数在 `+0x248`(512.0)；与 `+0x240` 贴图槽同住一个子结构（`0x9216FE` 读 `[ecx+0x11956C0]` 即 `+0x248` 为旁证）。
3. **`0.97266 − 0.96094` 实为 48/4096**，不是 32/4096；旧算式算错，不要拿它当「格宽 = 32/4096」的证明（该结论另由实测 UV 支撑）。
4. 追加两条本次实测纠正：**「1925」不存在**，真实宽乘数是 1920（1925 是反推舍入）；**`0x921780 movss xmm0,[esp+0x3c]` 读的不是 H**，那是 X 基准（`esp` 此时 = E，`[E+0x3c]`）；H 的读取在 `0x9217B7`（此时 `esp = E−0x0C`，`[E+0x30]`）。

### 2.3 「6 处」是怎么来的，错在哪 [实测确证]

| 你列的调用点 | 实测归属 | 是否独立安装点 |
|---|---|---|
| `0x79A0` / `0x79CD` | W2（封装 `0x7980`、安装器 `0x7680`、handler `0x6210`）/ W3（封装 `0x79B0`、handler `0x61A0`） | 各是独立点 |
| `0x7BD1` / `0x7BF8` | W4a / W4b：**同一封装 `0x7BB0` 的两条特征码命中**，同 handler `0x6120` 装到两个不同 exe 地址 | 一个封装、两个目标 |
| `0x7C30` / `0x7C60` | W5（封装 `0x7C10`）/ W6（封装 `0x7C40`），共用 handler `0x60A0` | 各是独立点 |

- `0x79A0`（`0x7980`→`0x6210`）与 `0x7C30`（`0x7C10`→`0x60A0`）**不是同模板重复**：安装器不同（`0x7680` vs `0x7110`）、handler 不同、目标不同；`ret 4` + `0xCC` 填充只是所有薄封装的共同骨架。
- 「6 处」口径实际只覆盖 W2/W3、W4a/W4b、W5/W6，**漏掉 W1、W7、W8、W9、W10、W11a/b 共 6 个目标**。
- 旧文档「仅 3 处」是把「封装函数本身无 call 引用」误当成「不装 hook」，实际封装被 C++ 对象表/`std::function` 调用。

### 2.4 宽度值从哪来（Q1 第三问）

- **运行时宽值取自引擎对象内被捕获的浮点数组**：基址 `0x10037AF0`、第二段 `0x10037B04`（= `AF0 + 0x960`），由捕获封装 `0x8230` 从引擎对象 `+4` 字段直接取址，stride 4。
- 公式（`0x10006040` 与 `0x10006210` 实测一致）：

```
idx = fontRec[0x29]*0x96 + fontRec[0x25]
w   = float32[ 0x10037AF0 + idx*4 + 0x204 ]
w  += [0x100275EC]      ; ASI 内建常量加数（31.0）
w  /= [0x10037B00]      ; 除数（捕获自引擎对象 +4）
w  += fontRec[0x2C]
w  *= fontRec[0x0C]     ; 宽度乘数 scale
```

- `fontRec` 在 **ASI 侧步长 `0x48`**（`+0x04/+0x0C` 乘数、`+0x25` 列参数、`+0x28` 主索引 ×`0x96`、`+0x29` 次索引、`+0x2C/+0x34` 加数）——**与 exe 侧 `0x1195478` 的 `0x258` 步长不是同一套结构，偏移不可互搬**。
- 资源：
  - `char_table.dat` **已解码**：`u32 表头计数 N + N 个 u32 小端码点（升序）`；当前游戏目录副本 14,324 B、N=3581（旧版 14,072 B / N=3517）；二分查找 `0x10005850`，装载 `0x100058D0`。作用只是码点白名单，**不存宽度**。
  - `whm_table.dat` **格式未解码**（780,676 B，头 u32 `0x150C`=5388，其后 `(u32,u32)` 成对；只存在于备份目录，当前 `plugins` 下没有），未定位到装载器 → 「宽度主来源是引擎对象数组而非该 dat」为**强推断，非确证**（见 §8-6）。
  - ASI 内建特表 `0x10006940`：对 `0x3001/0x300F/0xFF01/0xFF0C/0xFF1A/0xFF1B/0xFF1F/0xFF5E/0x2026` 给 advance +2。

### 2.5 一条必须写明的未确证（只影响「照抄旧补丁字节」）

W2/W3/W4a/W4b/W5/W6/W7/W8/W11a/b 的 target 原字节都是 **`E8`（call）**，而表里按统一口径写的是 `E9`。若真写 `E9`，跳过去时栈上没有返回地址，handler 的 `ret` 会弹到参数上——逻辑不成立。**更可能：安装器对原本 `E8` 的站点写 `E8 rel32`（保留 call 语义），只对非 call 站点（W1/W9/W10 等）写 `E9` + 自带 resume。**

本次只静态读到 `0x7110` 内部有 `sub eax,0xE8` 的原首字节判别，**没有逐字节确认最终写出的 opcode** → **[未确证]**，验证方法见 §8-1。这条不影响我们的方案（我们 hook 的是函数本体），但影响「照抄旧补丁」的可行性。

## 3. Q2：`0x6660` 画字 handler 逐参逆清

### 3.1 4 个参数（`__cdecl`，入口记 `E`）

| 位置 | 类型 | 语义 | 证据 |
|---|---|---|---|
| `arg1 [E+4]` | float | 归一化 X（先 `/ 状态对象 +0xC`，再 `[0,1.0]` 越界检查；quad 以它为中心） | 强推断（非原始像素） |
| `arg2 [E+8]` | float | 归一化 Y（与 `[-0.06558, 1.0]` 比较） | 强推断 |
| `arg3 [E+C]` | WCHAR | **UTF-16 码元，查找键 = `ch + 0x20`**；不是字体索引 | 实测确证 |
| `arg4 [E+10]` | dword | 仅兜底路径透传给 vft`+0x34`；主路径颜色取状态对象 `+0x18` | 强推断（颜色/标志） |

入口判定（实测）：`state+0x30 != 0` → 兜底；`iswprint(ch+0x20)` 为假 → 兜底；`ch+0x20 == 0x3000` → 静默跳过；`y` / `x` 越界 → 跳过。

### 3.2 quad 与 UV [实测确证]

- `0x5850` 二分排序码点表 `0x10037A80`，输出 `group = i >> 6`、`slot = i & 0x3F`。
- UV：`U0 = group*64/4096`、`U1 = (slot+1)*66/4096`、`V0 = (group+1)*64/4096`、`V1 = slot*66/4096`（基数 `0x100275D8 = 1/4096`）。
- 屏幕矩形：X 跨度 `32.0 / state+0xC`（加 `state+0x2C`）再乘回 `state+0xC`；Y 跨度 `state+0x10 * 0.067122`，`y_hi = span*0.953133 + y`、`y_lo = span*1.0 + y`；8 个 float 组成「两条 X + 两条 Y + 两组 UV」交给渲染器。

### 3.3 提交与贴图

- 提交走 **captured 渲染器对象 `0x10037AD8` 的 vtable**：`+0x40` 画 quad（thunk `0x6BD0`）、`+0x34` 兜底（`0x6B70`）、`+0x08` 设色（`0x6BF0`）。
- **ASI 的 IAT 只有 `KERNEL32` + `msvcrt`，无 d3d9/dxgi**；全 asi 对 `0x90A360 / 0x923140 / 0x8D4340 / 0x91B850 / 0x91C7C0 / 0x91BC80` 的静态引用均为 **0**。
- 贴图用字符串 `"font_chs"`（`0x100275C8`）经 vft`+0x10` 注册，不走 `fontRec+0x240`。
- 顶点 36 B / 缓冲 / 170 满批 / 最终提交是否复用引擎路径，**封装在 vtable 实现内部，静态不可见 → [未确证]**。

### 3.4 它如何绕过引擎 UV/宽度链路

- **实测确证**：`0x6660` 调用图只有 `0x1D50`(字符分类)、`0x6040`(进距/高度)、`0x5850`(查字形)、`0x6BF0`/`0x6BD0`/`0x6B70`(vtable)、`0x1D4C8`(栈 cookie)；**不含** `0x91C7C0` / `0x91C7A0` / `0x91BC80`，也不读写 `A+0x24`。
- 前进量来自自有 whm 表：`0x6040` 里 `idx = state[0x29]*0x96 + state[0x25]` → `w = whm[idx] + 31` → `/ 0x10037B00` → `+ state[0x2C]` → `* state[0x0C]`。**表驱动，不等于字号**。
- 结论：旧补丁在逐字层**整体旁路**引擎测宽/宽度槽——测量端点被 `0x6210/0x61A0/0x6120/0x60A0` 接管，绘制端点由 `0x6660` 接管。两个 `0x6660` hook 的真实 exe 目标静态无法定位（thunk `0x78C0`/`0x78F0`，槽 `0x10035318`/`0x100353D0`，运行期特征扫描回填）。

### 3.5 与我们的资源差异（照抄必须先改）

| 项 | 旧补丁 | 我方 |
|---|---|---|
| 图集格 | 64 texel 步距、66 含 2 px 间隙（`group=i>>6`, `slot=i&0x3F`） | **32×32**，128 列 × 128 行（`col=idx%128`, `row=idx/128`） |
| UV 基数 | `1/4096` | `1/4096`（相同） |
| 格形状 | 非 1:1（64 横 / 66 纵） | 1:1 |
| 宽度来源 | 自有 whm 表 | 引擎测宽 + 我们的校正 |

→ 直接搬 `0x6660` 会把格位切错，**必须整体替换格子参数**。这也是「不推荐自绘」的第二个理由。

## 4. Q3：推荐路线

### 4.1 三个可选动作（现状已接管测宽，所以问题变成「改哪个值」）

| | **A：改 `StubCw` 返回值（推荐）** | B：另加 W 槽覆写（对照实验） | C：转 inline 自绘（保底） |
|---|---|---|---|
| 动作 | `H` → `H·Hv/Wv` | 在 `StubDraw` 里补写 `[esp+2Ch]` | 复刻 `0x6660` 式自绘 |
| 改动量 | **2–6 条指令 + 1 个 C 辅助函数** | +2 条指令，但与 A 冲突 | 150+ 行、新 hook 1–3 处 |
| 四边形宽度 | 对 | 对 | 对 |
| 逐字字距 | **对（同源）** | **错 → 汉字重叠**（pen 走 `0x92197E`，不经 W 槽） | 对（自管） |
| 整行测宽/换行 | **对（同源）** | 错（14 处调用点仍拿旧值） | 自算 |
| 风险 | FPU 栈平衡、`A8` 依赖 | 必现重叠 + 双源（同一字形两个宽度来源） | 顶点缓冲/满批/vtable 崩溃面最大 |
| 可回退 | 改回一行 | 删两句 | 摘整套 |

### 4.2 为什么是 A

1. **唯一正确的位置**：`0x91C7C0` 是四边形宽度（`0x921537`）、pen 字距（`0x92197E`）、整行测宽/换行（12 处）的**共同唯一来源**。在这里给出正确的归一化宽度，四条消费路径自动一致，没有「方字 + 3 px 步距」的自相矛盾。
2. **旧补丁也这么做**：它的 W5/W6 就装在 `0x92197E` / `0x92381E` 两个前进量调用点上（§2.2），等于用两个 hook 换我们一个返回值。我们更省。
3. **现有代码已经到位 90%**：`StubCw` 的 `E9` 安装、trampoline、`IsCjkGlyph` 双查法、`6` 字节边界都已验证过（`InstallProbe` 会校验原字节），只需换返回值。
4. **不动 UV、不新增特征码、不新 hook**：两个 UV hook 原样保留，签名池不变，`count==1` 的严格校验不变。
5. **顺带把过宽风险反向消掉**：宽度从 30.22 降到 17.00，`0x921185` 的溢出限幅更不可能被触发（现在是过宽，改后收窄）。

### 4.3 为什么不是 B

只改 `A+0x24` 会让四边形变 17 px，但 pen 由 `0x92197E` 那次独立调用推进，仍是旧值（引擎原样 3.1186 px 或 `StubCw` 的 30.22 px）——**要么重叠、要么间距荒**。B 只能用来做「隔离几何宽度」的一次对照，不能作为交付形态；而且它与 A 同时存在就是双源，排障时无法判断是哪个值生效。

### 4.4 为什么不是 C

旧补丁能自绘，是因为它**整套字体层都是自己的**（自有图集、自有 whm 表、自有测量、自有绘制、自己捕获的渲染器对象）。我们只有 UV + 宽度两处；走自绘等于把 `0x90A360`（36 B 顶点 / 170 满批）、`0x923140`（绑 `fontRec+0x240`）、`0x8D4340`（只 2 个调用点）整条链复刻一遍，收益仅是「不依赖引擎宽度」，代价是崩溃面从 1 个返回值变成一条链，还要改格子参数（§3.5）。留作 A 不通时的保底。

### 5.1 改哪个函数：`StubCw`（`font.cpp:129-146`）

    inc   dword ptr [g_cwCjk]

### 5.2 改成什么（两个变体，选一个）

**变体 1（推荐，绝对正确、不依赖常量）—— 改为调用 C 辅助函数重算**

```asm
    inc   dword ptr [g_cwCjk]
    pushad                            // 只存 GPR，不碰 FPU
    call  ComputeCjkWidth             // 内部写 float g_wcjk；自平衡 FPU，不返回值
    popad
    fld   dword ptr [g_wcjk]          // ST0 = W' = H × Hv / Wv
    ret
```

`ComputeCjkWidth`（`extern "C" __cdecl`，单次约 3 次内存读 + 几条浮点，开销可忽略）：

```c
extern "C" void __cdecl ComputeCjkWidth(void)
{
    int wv = *(volatile int*)(g_imgBase + 0xC1C884);      // 0x105C884 视口宽
    int hv = *(volatile int*)(g_imgBase + 0xC1C880);      // 0x105C880 视口高
    float a8 = *(volatile float*)(g_imgBase + 0xC366A8);  // 0x10366A8 高度基准
    float h  = a8 * 0.065580f;                            // = 0x91C7A0 的返回值
    if (wv <= 0 || hv <= 0) { wv = 800; hv = 600; }        // 兜底 800x600
    if (!(h > 0.f) || h > 1.f) h = 0.01573888f;           // NaN / A8 未初始化保护
    g_wcjk = h * (float)hv / (float)wv;
}
```

- `g_imgBase` 已是模块基址（`font.cpp:486`：`textBase − 0x1000`），故 `0x105C884 → +0xC1C884`、`0x10366A8 → +0xC366A8`。
- **代价**：不再调用 `0x91C7A0`，H 改由我们自己按同一公式算。公式与引擎完全同源（`A8 × 0.06558`），但多了一个「A8 读错就全错」的依赖（§8-2 有兜底与验证）。

**变体 2（最小改动，但依赖运行期比值）—— 保留原调用，后面接一个乘法**

```asm
    call  dword ptr [g_atCwHeight]    // ST0 = H
    fld   dword ptr [g_wRatio]        // ST0 = ratio, ST1 = H
    fmulp st(1), st                   // ST0 = H * ratio
    ret
```

`g_wRatio` 需在分辨率变化时刷新（`WM_SIZE` 或每帧一次读 `Hv/Wv`）。若忘记刷新，切分辨率后会偏宽/偏窄。

> 两者都**不弹参数**（`__cdecl`，调用方 `0x921553 add esp,0xc` 清三处 push 为旁证），都只以 `ST(0)` 交付返回值。

### 5.3 顺手清理

- `font.cpp:75` `g_kAdv = 0.5625f` 已是**死常量**（全文件无引用），可删；不要把它再塞回任何栈槽。
- `StubDraw` 的 236-242 保持现状（只留证、不覆写），**不要**恢复 W 槽写。

### 5.4 顺序（关键：先验不崩，再验数值）

1. 备份（§9.3）→ 2. 改 `StubCw` + 加 `ComputeCjkWidth` → 3. 编译（`src\build.bat`，输出 `out\z_gta4cn.asi`）→ 4. **先只装 hook、命中路径仍 `ret` 原值**（确认安装/FPU 平衡/不崩）→ 5. 打开新返回路径，跑 §6 → 6. 通过后再谈部署。

第 4 步很重要：`StubCw` 命中分支新增了 `pushad/popad` 和一条 `fld`，任何 ST 栈不平衡都会在**几秒内**崩（与文字内容无关），先隔离掉这个变量。

## 7. 风险与共存

| 风险 | 说明 | 判据 / 处置 |
|---|---|---|
| FPU 栈不平衡 | 命中分支新增 `fld`（以及变体 1 的 `call`），多压/少弹 ST 条目；崩点可能离本函数很远 | **进游戏几秒内崩**（与文字内容无关）→ 先做 §5.4 第 4 步 |
