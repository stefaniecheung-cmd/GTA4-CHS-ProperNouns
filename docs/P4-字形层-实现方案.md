# P4 字形层·代码侧 实现方案（2026-11-08）

> 本文替代「反复改栈槽试错」的做法。以下每条结论都标注了证据来源；
> 未证实的一律写「待证」，不再当作前提使用。

## 一、已证实的链路（不要再重新定位）

```
0x921140  入口分流（cmp [0x10366C8],0 → 路径 B）
  └ 0x921534  路径 B：查宽度 0x91C7C0、查槽位 0x91BC80、算 UV
      └ 0x92159E  ← hook ① StubMap（char → 映射表槽位）
      └ 0x92176E  ← hook ② StubDraw（UV 计算完成、组 quad 参数前）
          └ 0x9217EA call 0x91B850  字形四边形
              └ 0x90A360  写顶点（每顶点 36 B，缓冲 0x1195F70，满 170 提交）
                  └ 0x923140  绑 fontRec[font]+0x240 贴图 → 0x8D4340 提交
```

证据：
- 三探针实测（0x91C7C0 测宽 / 0x90A360 写顶点 / 0x91B850 四边形）计数一致放大，说明这条链在真机高频执行。
- `0x8D4340` 全游戏只有 2 个调用点，都在 `0x923140` 内 → 文字顶点唯一通道。
- `fontdbg.txt`：我们的 UV 已写进 quad 参数（`0.96094 / 0.02344 / 0.97266` 与 idx 严格对应）。

## 二、字体号实测：菜单文字走 font1

一次取证（改门前版本）：

```
sdByFont: f0=2118  f1=18324  f2=0  f3=0
lookN=2118  hit=0        ← font0 那 2,118 次画的是数字/英文，一个汉字都没命中
```

结论：**GTA IV 的菜单/页签文字用 font1**，HUD 数字用 font0。
两处 hook 原本都有 `dl==0` 门 → font1 完全没被接管 → 页签全是 `!`。
门已移除，扩到 font1/font3 后实测：`sdN=513,992 / sdxN=388,699 / uvApplied: f0=324,167 f1=11,538 f3=52,994`，
即 **font1 的汉字现在确实被我们覆写 UV 了**。

## 三、为什么「换贴图 + 覆写 UV」会让全部文字消失（根因）

反汇编 `0x9216BF` 起的 UV 计算（font≠2 分支）：

```
0x9216FE  xmm2 = [0xfe88e8] / [fontRec+0x240+8]     ; = 1.0 / 512.0
0x921709  xmm1 = [fontRec+0x246]                    ; = 40.0
0x921711  xmm4 = [fontRec+0x250]                    ; = 39.5
0x921719  xmm6 = [fontRec+0x24C]                    ; = 4.0
0x921721  si >>= 4 (行)
0x92172F~0x92174B   V = (行 - 基值) * (40/512) + 4/512 - 39.5/512
0x9216C9  U = (si & 0xF) * [0xfe8778]
```

**这套公式产出的是「512² 图集坐标」。** 贴图换成 4096 之后，引擎给非汉字字符算出的 UV 只能采到
4096 图的左上 1/8（0~0.125）区域；而汉字由我们覆写成「4096 坐标」（0~1）。
两套坐标系混在同一张贴图上 → 同一批次无法自洽。
真机表现：`!` 变成彻底空白（采样落到图集空白区 / 尺寸塌陷）。

**同样地，把 font1/font3 的 `+0x240` 指针改指 font0 的图集（本轮 `RetargetFontTextures`）也是错的**：
它让 ASCII 的 512 坐标系去采 4096 图，必然乱或空。

## 四、三条可选路线

### 方案 A（推荐，已细化为「对润色线零影响」版）：图集镜像 ASCII + 汉字区下移
- **图集重烘焙**：4096 图集的 **左上 512×512 区块**按原版 `font1`/`font3` 的布局（16 列、行高 40）1:1 画入 ASCII / 标点镜像；
  汉字改从 **y = 512 起排**（行基址 `rowBase = 16`），顺序与索引不变。
- **`glyphs.dat` 逐字节不变**：索引 i → 行 `16 + i/128`、列 `i%128`。换句话说只改 UV 计算里的行基址常量，
  字符表与润色线无关的那部分零改动。
- font1/font3 的 `+0x240` 指向我们的 4096 图集（**字体加载完成后一次性写，不做周期重申**）。
- 汉字：我们覆写 UV（4096 坐标，含 `rowBase=16`）；ASCII/标点：**不覆写**，走引擎原 UV → 正好命中左上镜像区。
- 优点：一张图同时满足两套坐标；混排零风险；**不需要动 `glyphs.dat`，也不需要润色线配合**。
- 代价：重烘焙一次图集 + 重打三章 wtd（各留 `.bak_p4b`）。

> 后续若润色线新增了字符（新译文里有图集没有的字），走「追加」：在汉字区尾部续排新格、`glyphs.dat` 只追加条目，
> 已有索引一个都不变。**任何时候都不做重排。**

### 方案 B：汉字走独立字体槽
- 保留 font0/1/3 原图集与 512 坐标系不动；把 font2（现为空槽）做成汉字字体，指我们的 4096 图集；
- 汉字绘制时把 font index 切到 2，提交后切回。
- 优点：完全不动图集；ASCII 一辈子走原路径。
- 代价：会打断引擎的批量顶点提交顺序（170 顶点一批、一次绑一张图），需要在批次边界切换，风险在引擎内部状态。

### 方案 C：调用点接管（旧补丁路线）
- 在「画一个字」的调用点打 inline hook，handler 自己算 quad、自己绑贴图、自己提交。
- 优点：彻底绕开引擎字体系统，与 font 号无关，一次覆盖全部 UI 与游戏内文本。
- 代价：要自己实现 quad 装配与 D3D 提交，工作量最大；且旧补丁 asi 侧的 RVA 全是 asi 自己的，不能直接抄，需要在 exe 侧重新用签名定位。

## 五、按方案 A 的实施步骤（每步都有验收物）

### 1. 栈槽语义表（已核实，2026-11-08）

函数帧：`sub esp,0x30` + `push esi` + `push edi`，退出时 `pop edi / pop esi / add esp,0x30 / ret`。
记 **A = sub esp 之后的 esp**，则 hook 入口（0x92176E）处 esp = A − 8。

| 槽（hook 入口 esp 偏移） | 绝对 | 语义 | 证据 |
|---|---|---|---|
| hook 入口 esp = A−8 | — | — | 0x9217F2 `pop edi/pop esi/add esp,0x30/ret` 反推 |
| `[esp+28h]` | A+0x20 | **宽度（UV 增量，U_right = U + 此值）** | 0x9217A6 `addss xmm7,[esp+0x30]`，此刻 esp=A−0x10（已两次 push）→ A+0x20 |
| A+0x00 ~ A+0x0F | — | 传给 0x91B850 的第 1 个 float 块 | 0x9217B1/0x9217D8/0x9217E4 写入 |
| A+0x14 ~ A+0x23 | — | 传给 0x91B850 的第 2 个 float 块（含 UV） | 0x9217AC `lea eax,[esp+0x20]`…… |
| A+0x2C | — | **特殊字符标志**：非 0 直接 `jne 0x9217f2` 不画 | 0x921763 `cmp byte [esp+0x34],0` |
| A+0x34 / A+0x38 / A+0x40 | — | 调用方传入的 x / y / 参数 | 0x921780 / 0x921790 / 0x92178C |

**重要修正**：`[esp+28h]` 才是引擎真正读取的宽度槽（我此前写 `[esp+1Ch]`、更早写 `[esp+30h]` 都是错的）。
但引擎自己的值就是 `4.0/512 = 0.0078125`，与我们写的 `32/4096` 完全相同 → **这个写操作等价于 no-op，它不是「文字消失」的原因**。

**`A+0x2C` 这个标志位要特别注意**：当 `si == 0xFD` 或 `si == 0xFFFF` 时被置 1，随后 `0x921763` 直接跳过绘制。
所以 `StubMap` 里把 `si` 置 0 之后必须确认没有触发 `0x9215DB` 的 `cmove` 分支（待运行期取证）。

**仍未证实的部分（写清楚，不当前提）**：在「贴图指我们 4096 图集 + 全字体覆写 UV」的组合下，
连 ASCII 都应能显示（512 坐标只采到图集左上 1/8，那里是第 0~255 号汉字格，属可见内容），
真机却是彻底空白。这一条现有静态证据无法解释，必须在 A 落地后带顶点缓冲 dump 一起定位。

### 2. 资源（下一步，纯离线，不依赖游戏）

解出原版 font1/font3 的 512 图集 → 合成新 4096 图集（左上 512×512 1:1 镜像 + 汉字区重排）
→ 重生成 `glyphs.dat` → 重打 base/TLAD/TBoGT 三份 wtd（各留 `.bak_p4b`）。

### 3. 代码

删 `RetargetFontTextures` 的周期重申，改为字体加载完成后一次性写；
`AdjustUV` 改指向重排后的索引基址；ASCII 分支不覆写 UV；`A+0x2C` 标志位加保护。

### 4. 验证闸

base 章进菜单抓图 → 页签出现汉字；再验 TLAD/TBoGT。每次验证同时落一份顶点缓冲 dump（文字 UV 与贴图指针），
避免再靠画面单点判断。

### 5. 收尾

删探针（Pr0/Pr1/Pr2）与全部诊断计数，写交接。
