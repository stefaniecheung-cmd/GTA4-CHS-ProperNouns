# P4 前置：GTA4 文本与字形渲染链路理解

调查时间：2026-11-08
目的：在做字体层之前，先弄清「GXT 文本 → 屏幕像素」这条链路上每个环节由谁负责，避免改错层。

结论先行：**引擎只认位图字体图集，没有字符表概念；中文字形映射完全由旧补丁的 asi 承担。我们的译文已全部就位，字形缺口只有 5 个字。**

## 一、链路总览

```
GXT(UTF-16LE) ──引擎解析──> 文本字符串 ──引擎绘制──> 查字体图集 ──> 屏幕
                                   │                      ▲
                                   │                      │
                              （旧补丁 hook 这层）    platform:/textures/fonts_*
                                   │                      │
                         char_table.dat（码点表）      fonts.wtd（RSC5 压缩图集）
                         whm_table.dat（crc→UTF-8 译文）
                         custom_translations.json
```

## 二、已验证的事实（有直接证据）

### 1. 引擎侧的字体资源
- `GTAIV.exe` 内存在字符串 `platform:/textures/fonts_`，相邻还有 `font1`、`font3`、`font4`、`fonts_j`。
  → 字体走 RAGE 虚拟路径 `platform:/textures/`，且有**多套字体槽**（正文、手写体等各一页图集）。
- `GTAIV.exe` 内**搜不到** `char_table`、`whm`、`.wtd`、`american.gxt` 这些字面量。
  → 字符表与 whm 表**不是引擎资源**，引擎也不知道它们存在。

### 2. fonts.wtd 的物理形态
- magic = `RSC\x05`（RAGE 资源版本 5），第 8 字节起是 **zlib 流**（`78 da` 开头），即「RSC5 头 + zlib 压缩的纹理字典」。
- 解压后大小：

| 文件 | 压缩后 | 解压后 | 推算图集 |
|---|---|---|---|
| 原版 `pc\textures\fonts.wtd` | 101,044 B | 2,101,248 B | 约 1024×1024 |
| 中文版 `update\pc\textures\fonts.wtd` | 2,555,345 B | 6,291,456 B | **2048×2048 DXT5**（2048²×1.5 = 6,291,456，数值精确吻合） |

- 解压后开头是 `84 53 69 00`，不是 `DDS ` 魔数 → 图集外面还包了一层 RAGE 资源描述（指针表 + 纹理头），**不能直接当 DDS 替换**。

### 3. char_table.dat（14,324 B）
- 结构：`u32 count = 3,580` + 3,580 个 `u32` Unicode 码点，合计 3,581 个 u32 = 14,324 B，**尺寸完全吻合**。
- 码点升序排列：0x2014（—）、0x3001（、）、0x3002（。）、0x3007（〇）、0x300A（《）… 0x4E00（一）、0x4E01（丁）…
- 位置：`plugins\GTA4.CHS\char_table.dat` —— 在**补丁目录**里，不在 `update\`。

### 4. whm_table.dat（780,676 B）
- 结构：`u32 count = 5,388` + 5,388 条 `[u32 hash][u32 offset]`（4 + 43,104 = 43,108 字节表头），其后是 UTF-8 文本区，逐条以 `\0` 结尾。
- 尾部内容直接可读中文：`…的上城 马士堡水烟 和用来喝高级干椰的酒?。`
  → 它是**一张 crc→UTF-8 译文表**，用途是运行时按 crc 替换界面文本（不经 GXT）。名字叫 whm 但实际是替换表。

### 5. 旧补丁 asi 的构成
`GTA4.CHS.asi`（232,960 B）内可见：
- 符号 `gta_font::register_patches`，带 **lambda_1 ~ lambda_14** → 字体相关共 **14 个补丁点**；
- 符号 `gta_whm::register_patches`，带 lambda_1 → whm 表相关 1 处；
- 内嵌 utf8cpp（`invalid_utf8` / `invalid_utf16` 异常类）→ 自己做 UTF-8 ↔ UTF-16 转换；
- 字符串 `char_table.dat`、`whm_table.dat`、`custom_translations.json`、`font_chs`。

→ 旧补丁的字体方案是「**hook 引擎绘制 + 自带码点表 + 自带替换表**」，不是单纯换资源文件。

## 三、关于「中文双字节」的结论

- GXT 里文本是 UTF-16LE，**长度以字符计不以字节计**，所以中文不会因为双字节被截断。
- 真正的风险是**显示宽度**：同字数下中文占约两倍像素。这就是质检里 44 条「单行超宽」、34 条「整体偏长」的来源，属观感问题，不会崩。
- 渲染层把字符映射到图集槽位时，若码点不在 char_table 中，画出来是空白或方块——这是**字形缺失**，与编码无关。

## 五、P4 的两条路线（成本差距很大）

### 路线 A：零风险——改词规避（约 10 分钟）
把 7 条里的 5 个缺字换掉，完全不碰字体文件：
- 卓越极限 9 → 巅峰极限 9
- 西堤摩托车行 → 西岸摩托车行
- 遭犁过 → 遭碾平
- 本辖区内 → 本区域内
- 军队式围剿 → 军队式镇压

优点：不动图集、不碰 hook、不会引入乱码。缺点：治标，字形依赖旧补丁这一点没变。

### 路线 B：自建字形层（真正的 P4，工作量大）
按旧补丁已验证的路子重做：把 TTF 渲染成 2048×2048（或更大）图集 → 生成自己的 char_table 与度量表 → hook 引擎字形索引 → 打补丁。需要先逆向 `gta_font` 那 14 个补丁点对应的引擎函数，属于「没有源码、只有特征码」的硬活。
优点：彻底摆脱旧补丁。缺点：周期长、失败面大，且目前中文能正常显示，收益主要是「干净安装可用」。

## 六、尚未验证、需在 P4 前补的

1. 引擎取字形的**具体函数与索引方式**（码点直接当槽位，还是查表？）——需反汇编 `platform:/textures/fonts_` 的交叉引用。
2. 图集内**网格排布与字形尺寸**（32×32、每格留多少内边距）。
3. `platform:/textures/fonts_*` 是否支持**多页图集**（若支持，未来扩充汉字不受单页容量限制）。
4. 三个章节（base / TLAD / TBoGT）是否各有一套独立字体图集（目前 update\ 下确实是三份 wtd）。
