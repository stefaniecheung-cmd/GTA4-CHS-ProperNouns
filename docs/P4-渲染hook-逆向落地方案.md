## 0. 一页纸结论

### 0.1 本轮最重要的一条：矛盾已经不再是「解释不了」

上一轮把「接管扩到 font1/font3 + 贴图重定向 4096 图集」之后，真机**所有文字彻底消失（连 ASCII 也没了）**，静态证据（UV 对、指针统一、资源正常）解释不了。这一轮的真机取证日志 `chs\logs\fontdbg.txt`（2026-11-08 20:32:15，正是那一轮失败运行）已经把答案落到了盘上：

| 实测（`fontdbg.txt`） | 数值 | 含义 |
|---|---|---|
| `probe cw / vx / bq` | 6,693,732 / 1,738,124 / 1,738,124 | 测宽调用 669 万次；`0x90A360` 写顶点 **173.8 万次**；`0x91B850` quad 生成 173.8 万次 |
| `sdN / sdxN` | 1,738,124 / 1,361,436 | StubDraw 进入 173.8 万次，其中我们的 UV 生效 136.1 万次 |
| `sdByFont` 逐字体 | f0=1,604,241　f1=12,888　f3=120,995 | 加总 **严格等于** `sdN` |
| `uvApplied` 逐字体 | f0=1,228,912　f1=11,538　f3=120,986 | 加总 **严格等于** `hit`(1,361,436) |
| `tex[4]` | `0x48274250` / `0x48274250` / `0` / `0x48274250` | font0/font1/font3 **同指针且非空**；font2 无贴图 |
| 顶点样本 ×8 | 见 §1.3 | **x 跨度恒为 3.1186 px，y 跨度恒定 17.0 px** |

**结论：文字是被「画」了的，不是被整批丢弃的。** 173.8 万次 quad 生成与 173.8 万次顶点写入一一对应，顶点里位置与 UV 成对完整。真正的问题是 **quad 被压成了 3.1186 px × 17.0 px 的竖条**（宽高比 1 : 5.45），在 1920 宽的画面上肉眼等同于「没有字」。

这一条把「全黑」从玄学拉回到一个可测量、可归因的单变量：**宽度轴**。

### 0.3 新增主因假说 H2：**宽度层根本没被接管**

这是本轮的实质判断，并且有结构性证据：

- 旧参考补丁 `GTA4.CHS.asi` 在**四层**都打了 hook：取串 → 编码 → **宽度** → 绘制。宽度层就有 `E9 jmp` 两处（`0x79A0` / `0x79CD`）、单字宽两处（`0x7BD1` / `0x7BF8`）、可打印/度量判定两处（`0x7C30` / `0x7C60`）。
- 自研补丁只打了**两处**：`0x92159E`（char→槽位映射）与 `0x92176E`（绘制前重算 UV）。宽度函数 `0x91C7C0` **只装了纯计数探针**（`gta4cn.log`: `probe 0 at 0x014FC7C0 len=6`），一次也没被接管。
- 于是：UV 是我们逐字算的（正确），**前瞻宽度仍是引擎按原表算的**。原表里没有我们的码点，引擎只能给兜底值 —— 实测这个兜底值让 x 前进量恒为 3.1186 px，与字形无关。

换句话说：**我们只改了「贴哪一块图」，没改「这一步该走多宽」。** 字被画在正确的位置、取自正确的格位，但一个字只占 3 个像素。

> 该假说的证伪判据见 §4 实验 E3。若 E3 显示宽度随字变化，则退回 §3.4 的 H1（栈槽错位），仍不影响「宽度轴」这个定位。

### 0.4 工具主线：REA，卡点只有一个 patch 版本

用户确认的「REA」= `https://github.com/morluto/rea`（REA: Reverse Engineer Anything，npm 包 `rea-agents`，MIT）。**它是把逆向工具接给 agent 的 MCP 桥接框架，本身不带反汇编引擎**；native 分析必须挂外部后端，本机现成的是 **Ghidra 12.2 @ `C:\Game\_tools\ghidra_12.2_PUBLIC`**（`application.version=12.2`，`analyzeHeadless.bat` 在位）。

关键好处：REA 走「导入私有不可变快照 → 按需定点查询」，**不是 GUI 全量 auto-analysis**，因此很可能绕开之前两次 `Java heap space` 的死结。**但这是推断，必须首跑验证。**

唯一硬卡点：`rea-agents@6.8.0` 的 `engines` 是 `^22.23.4 || ^24.22.1 || >=26.12.1`，本机 `node v22.23.2` —— **差一个 patch**。

### 0.5 图集：`3,597` 不是容量，是表条目数

- `3,597` = `glyphs.dat` 头部 `u32` 值（14,392 B = 4 + 3,597×4），**映射表条目数**，不是贴图能切出的格数。
- 物理槽位 = `kCols × (kAtlas / kCell)` = 128 × (4096/32) = **16,384**（`font.cpp:16-18`）；当前只用到 idx 3,309 / 16,384 ≈ 20.2%。
- 所以「余量 250 格」是**表记录余量**（3,597 − 3,347），不是贴图面积余量。真正的瓶颈是表上限，而表是可以追加的。
- 按 Heaps' law 三档预测完成时需 5,827 / 6,159 / 6,510 格（§6.4），**全部落在 16,384 内**；结论：贴图够用，表需要扩容，扩容只需追加、不必重排。

### 2.3 三处对旧口径的修正（会直接影响后人判断，务必以本节为准）

**R1 · 「两处 hook 原本都有 `dl==0` 门」在当前部署件里不存在。**
对 `plugins\z_gta4cn.asi` 的 `.text` 扫描 `80 FA 00`（`cmp dl,0`）与 `80 F9 00`（`cmp cl,0`）均 **0 命中**；引擎侧 `0x921140` 里唯一的字体比较是 `font==3`（`0x92114C`），路径 B 的分支条件是 `font==2`（`0x92158E` / `0x9215FC`）。当前两道门是：StubMap 的查表命中门（ASI `0x1000B3E6 85 C0`）与 StubDraw 的 `g_idx == -1` 门（ASI `0x1000B320 83 3D 34 20 03 10 FF`）。
→ 「页签全 `!`」的因果链属于**更早一版 stub**（该版在 ASI 自己的代码里比较字体号），而 `dl` 门**从来不在 `GTAIV.exe` 的 `.text` 里**。所以「在 exe 里扫 `cmp dl,0` 得 0 命中」是方法错了，不是证据缺失。**结论保留，取证路径作废。**

**R2 · fontRec 度量常量偏移校正。**
旧笔记记的是 `+0x246 / +0x24C / +0x250`；按写入指令实测定为 `+0x24C(40.0) / +0x250(4.0) / +0x254(39.5)`，U 除数在 `+0x248`（= 512.0）。以 `0x91F384..3AC` 那五条 `C7 05` 立即数的目标地址为唯一依据（`0x11956BC/C0/C4/C8/CC` 减 `fontRec` 基址 `0x1195478`）。
→ 这条很要紧：`0x9216BF` 那段的 `ecx` 是记录内嵌子对象指针，其基址正是 `0x11956B8`（= `fontRec+0x240`，同时也是**贴图槽**）。也就是说「贴图指针」和「度量常量」住在同一个小结构里，**这解释了为什么只改指针不改常量会出事**。

**R3 · `0.97266` 那组 UV 数据自相矛盾。**
`0.97266 − 0.96094 = 0.01172 = 48/4096`，而正确格宽是 `32/4096 = 0.0078125`；且 `0.02344×4096 = 96 → row 3`，而 `idx 379` 的 `row = 2`。本轮真机成对样本（§1.3）里 `ΔU` 与 `ΔV` 恒为 `0.0078125`、`w=0.00781`、`idx` 与行列严格自洽。
→ 结论：**UV 公式与 `AdjustUV` 是对的**，那三个数来源存疑，不再作为「坐标系不匹配」的证据。**候选②里「UV 口径错」这一支也随之关闭。**（这一条是本轮唯一一处推翻上一轮硬事实的地方，按「指到字节」原则必须写在这里。）

## 3. 核心矛盾：三个候选 + 判据

> 判据统一写成「**读什么 / 看到什么 → 结论**」，全部可在下一窗口当场执行。

### 3.1 候选①：A+0x2C 特殊字符标志被置 1，直接跳过绘制

**机理（已 byte 级证实）**：
- 标志位在帧内 A+0x2C（= `[esp+0x34]`），入口 `0x92155D` 清零；
- `si == 0xFD` → `0x9215D0` 置 1；`si == 0xFFFF` → `0x9215EF` `cmove` 置 1；
- 检查点在 `0x921763`，非 0 则 `jne 0x9217F2`，从 `0x9217F2` 起只有 4 条指令 `pop edi / pop esi / add esp,0x30 / ret` → **只跳过当前这一个字，不跳出外层循环**（外层循环 `0x921952`–`0x9219A8`，串尾 `0x9219B0 push -1; call 0x923140` 全量 flush）。
- 跳过时不触碰计数 `0x1195EA0`、不写缓冲 `0x1195F70`、不调 `0x91B850`。

**为什么「未排除」**：`lookN − sdN = 299,182`（14.7%）。这批字查过表但没进 StubDraw，而标志检查正好在 StubDraw 原点之前，是唯一能整批消失的口子。
但也存在别的解释：`si` 走原链后被引擎自己判成 `0xFFFF`（原表无此码点）→ 置 1 → 跳过，这属于**引擎正常行为**。
→ 判据见 **E1**。

### 3.2 候选②：批次绑到的不是我们以为那张图

**排除依据（三轮交叉）**：
1. 部署件哈希 = 已校验件哈希（`7E18E6DE…`，1,590,798 B），该件内含 16,777,216 B（4096²×1 B）图集段；
2. 运行期 `tex[0] == tex[1] == tex[3] = 0x48274250` **非空**，说明纹理创建成功、`RetargetFontTextures` 生效；
3. `0x921777` 那道门（`cmp dword[eax+0x11956B8],0 / je 0x9217F2`）若命中，该字体一个字都不会画；而 f0/f1/f3 都有 10 万～160 万次绘制。

**唯一残留疑点**：`0x48274250` 是不是**那张 4096**。静态无法从指针值判断 —— 需要 `IDirect3DTexture9::GetLevelDesc`。→ 判据见 **E2**（成本很低，一次调用）。
但即便它是 512 旧图，也解释不了「3.1186 px 宽度」这件事，所以**②不是主因**。

### 3.3 候选③：quad 尺寸塌陷 —— 已确认（宽度轴）

**证据**：§1.3 的 8 个顶点样本，4 个不同字形，Δx 全部精确等于 3.1186 px，Δy 全部 −16.998 px。UV 逐字不同且完全正确。
**判定**：不是「尺寸为零/NaN」，而是**宽度被固定成一个与字形无关的常数**。高度 17.0 说明行高链路正常。
**含义**：candidate ③ 从「疑似」升级为「已确认」，并且**排除「整批丢弃、深度/混合全黑、贴图为空」这些解释**。

### 3.4 新增 H1 / H2：宽度为什么恒定

两条互斥机理，必须用 E3 分开：

| | 机理 | 支持证据 | 若成立，修法 |
|---|---|---|---|
| **H2**（主推） | 宽度层未被接管，引擎对未登记码点返回**兜底 advance** 3.1186 px | 旧补丁在宽度层有 6 个安装点，自研补丁 0 个；`0x91C7C0` 只有探针（`gta4cn.log`）；Δx 与字形无关 | 在宽度层加 hook（`0x91C7C0` / `0x91BC80`），把自己算的 advance 喂回去；或在引擎表里保证每个码点都有槽位 |
| **H1** | 位置宽度取自另一个栈槽，而该槽被 `si置0` 污染（取到 glyph 0 的度量） | StubMap 里 `xor esi,esi`（`font.cpp:140`）；若宽度的计算发生在 hook①**之后**，则 si=0 会让度量退到槽位 0 | 不要把 `si` 置 0，改为置成一个已知满宽参考槽，或保留原 si 只走 UV 旁路 |

**关键判别点（必须先确认）**：宽度计算 `0x91C7C0` 相对 hook① `0x92159E` 的**先后**。
- 若 `0x91C7C0` 在 `0x92159E` **之前**被调用 → si 污染不可能影响宽度 → **H1 直接出局，H2 成立**；
- 若在之后 → 两者都可能，需看 E3 的槽位数据。

（`0x921534` 路径 B 的内部调用顺序本轮未逐条落地，属 §附录 C 第 1 条未证实项。E3 的第一步就是把它钉死。）

## 4. 实验清单（可当场执行）

> 前置：全部实验都要先把 `chs\config.ini` 的 `EnableFontHook` 由 `false` 改回 `true`（**这是唯一写盘动作**，见 §8）。除 E0-补测与 E1/E3 需要改 `font.cpp` 重编一版**测试用** ASI 外，其余均为只读。

### E0 · 贴图指针 + 顶点前 36 B（**已完成 ~80%，不必重跑**）

**状态**：`chs\logs\fontdbg.txt` 已经给出了 `tex[4]`、`sdByFont`、`uvApplied`、`sdLast` 与 8 个完整顶点（位置 4×float + UV 4×float）。这就是原计划「先落一次 dump」的产物 —— **那一轮已经落过了，别再重跑一遍**。

**还缺的两项**（补测清单）：
1. `IDirect3DTexture9::GetLevelDesc` 的 `Width/Height/Format` —— 把 `0x48274250` 钉成「4096 还是 512」。
2. **逐字**的 `[esp+0x28] / [esp+0x2C] / [esp+0x30] / [esp+0x34]` 四槽原值 —— 现在只知道 `w=0.00781`，不知道另外三个槽。

**成功判据**：`Width==4096 && Height==4096 && Format` 与我们烘焙的 DDS 一致 → ②彻底结案，之后只谈宽度轴。
**失败判据**：`Width==512` → 说明 `RetargetFontTextures` 把三个字体指回了旧图，②重新立案，且「3.1186 宽度」要重新解释。

### E1 · 特殊字符标志记账（回答候选①）

**注入点**：`0x921763`（`80 7C 24 34 00`，3 字节）之前插一个只读 count stub，或在 StubDraw 里读 `[esp+0x34]`（hook 入口 `esp = A−8`，故 `[esp+0x3C]` = `A+0x34`… 以现有 `font.cpp` 的 `pushad` 之后再取，需按栈深换算，**这是唯一容易算错的地方，务必先打印一次 `esp` 自校验**）。

**记什么**：`(font, ch, flag, si_after)` 四元组，只记计数与前 64 个样本。

**成功判据（①成立）**：`flag==1` 的比例 ≈ 14.7%，且这些 `si_after` 主要是 `0xFFFF`/`0xFD`。
→ 那么「全黑」里有一部分字是**被引擎自己**判成缺字跳过的，属于「图集/表没覆盖」，修法是补表而**不是**改 UV。

**失败判据（①出局）**：`flag==1` 比例 ≪ 14.7%，或为 0。
→ 299,182 的缺口另有来源（串尾、路径 A 的字、`0x921533 ret` 快速路径），需要按 `0x10366C8` 分桶统计。

### E2 · 贴图身份（回答候选②，与 E0-补测同一件事，可合并）

**命令级做法**（不改游戏文件）：先按 §7.4 用 REA/Ghidra 把 `0x8D4CB0` 内部的设备对象 vtable 落到具体 `IDirect3DDevice9` 方法索引，再用一次 `GetLevelDesc` 调用验证；或用 `p4_wtd_parse2.py` 解析**部署件** `fonts.wtd`，得到条目数与每个条目的 `Width/Height`。
**成功判据**：wtd 内字体纹理 = 4096×4096 且只有一张 → ②结案。
**失败判据**：仍有一张 1024² / 512² 条目被 `"font1"`/`"font3"` 名占用 → 名字解析（`0x451C20`）拿到的可能不是我们换的那张，②重新立案。

### E3 · 宽度源（回答候选③/H1/H2，**最高优先**）

分三步，每步都有独立判据：

**E3-a（静态，0 成本）**：把 `0x921534`–`0x92159E` 之间逐条反汇编，标出 `0x91C7C0` 的 `call` 相对 `0x92159E` 的位置。
- 判据：`call 0x91C7C0` 地址 **< `0x92159E`** → **H1 出局**，H2 直接成立。

**E3-b（运行，需测试版 ASI）**：在 `0x9217EA` 之前（`0x9217E2` 附近）抓四个槽 `[esp+0x28] [esp+0x2C] [esp+0x30] [esp+0x34]` 与前一块的四个 float，逐字记录。
- **H2 判据**：四个槽里**没有任何一个**随字变化（尤其 `[esp+0x28]` 恒 = 0.0078125），且 block1 的 Δx 由某个**固定**槽推出 → H2 成立。
- **H1 判据**：存在一个槽在命中/未命中之间取值不同（命中时 = glyph0 度量），且 Δx 随该槽变化 → H1 成立。

**E3-c（决定性）**：把 `0x91C7C0` 的**返回值**按字符记账（该函数已被探针计数，只需加一个 4 字节环形缓冲存 `eax`）。
- **判据**：对全部 CJK 返回值恒为同一常数 → 兜底宽度确认；返回值随字变化 → 宽度其实是逐字的，问题在别处（回到 E3-b）。

**结果分支**：
- H2 成立 → 修法 = **补宽度层 hook**（见 §5 方案 A′）；
- H1 成立 → 修法 = **取消 `si置0`**（`font.cpp:140` 的 `xor esi,esi` 改成保留原 si，或改成「置成参考满宽槽」），这也是**最小改动**方案；
- 两者都不成立 → 落回「缩放因子 `0x105C880/87C/884/888` 为 0 或极小」，`0x91B850` 内 `mulss` 无 0/NaN 拦截（`0x91B8D6..E7`），需读这四个全局的实际值。

## 5. 方案 A / A′ 与方案 C：决策树

> 只给判据，不给「都试试」。任一分支一旦判据命中，就按该分支走下去，不要回头混做。

| 判据命中 | 结论 | 动作 |
|---|---|---|
| E2：wtd 里字体纹理 = 512² 或名字对不上 | 方案 A 的资源侧失败 | **转 C**：先把 fonts.wtd 正确烘焙与命名（`"font1"`/`"font3"` 两条都要 4096），再谈 hook |
| E0-补测：`tex[0]==0` | 纹理创建失败 | **转 C**：查 DDS 格式（`atlas_*.dds` 的 `pfFlags=0`、`fourCC` 空、`bpp=0` 未填，§6.1）与 wtd 封装 |
| E3：H2 成立 | 宽度层缺口 | **方案 A′**：在 `0x91C7C0`（测宽）与 `0x91BC80`（查槽位+字宽）上加 hook，返回我们自己的 advance；UV 侧维持现状不动 |
| E3：H1 成立 | `si置0` 污染 | **方案 A′**：只改 `font.cpp:140`（保留原 si），UV 仍走 `g_idx`。**改动最小，先试这个** |
| E1：`flag==1` 占 14.7% | 表覆盖不足 | 补表 + 追加图集（§6），不动 hook 逻辑 |

**明确的劝阻项**：继续在 `[esp+XX]` 偏移上打转没有意义。`g_w = 32/4096` 与引擎原值 `4.0/512 = 0.0078125` **数值完全相同**，这个写入是 no-op（§1.3 的 `w=0.00781` 已实测印证）。前两轮为此改错两次 `[esp+0x30]` / `[esp+0x1Ch]`，不要再碰。

**方案 C 是什么（保底路线）**：放弃「4096 自绘图集 + 改引擎 UV」这条，改回旧补丁已验证的路——**在引擎的原始 512 图集坐标系里工作**：图集只做 512² 的多页扩展或直接沿用旧补丁的 64 页方案（旧补丁 `cmp esi,0x3000` = 12,288 格），hook 只做「char → 槽位」映射，UV 完全交给引擎。代价：图集容量受限、需要多页，但**坐标系数值风险归零**。只有在 E2 判失败或 A′ 两轮仍不显字时才转。

## 6. 图集排布与容量（方案 A 侧，只追加永不重排）

### 6.1 当前排布（源码 + 资产双印证）

| 项 | 值 | 出处 |
|---|---|---|
| 图集边长 `kAtlas` | 4096 px | `font.cpp:16` |
| 列数 `kCols` | 128 | `font.cpp:17` |
| 格宽/高 `kCell` | 32×32 px | `font.cpp:18` |
| 行数 | 128（= 4096/32） | `font.cpp:334-336` 以 `row >= kCols` 判越界 |
| 映射 | `col = idx % 128`；`row = idx / 128` | `font.cpp:106-107` |
| UV | `cell = 32/4096`；`U=col*cell`；`V_top=row*cell`；`V_bot=(row+1)*cell` | `font.cpp:108-113` |
| 负载 | 16,777,216 B = 4096²×1 B（1 B/px） | `atlas_*.dds` 去 128 B 头 |

**资产健康度（脚本实测，`probe_atlas_layout.py`）**：
`glyph_map_final.tsv` 3,309 行，idx 0–3,308，**严格单调 +1、0 空洞、0 重复**；`char_table_new.dat`（13,240 B = 4 + 3,309×4）与 TSV 同序同码点；`glyphs.dat`（14,392 B = 4 + 3,597×4）为运行期加载表，其中 13 条 `<0x100` 残留槽位不映射（属映射空洞，非编号空洞），首项 `0x0E0C` 越序、成因**未证实**。

**未证实**：DDS 头 `pfFlags=0`、`fourCC` 空、`bpp=0` 未填 —— 到底是 luminance8 还是 palette8，需读 wtd 内纹理头。这直接影响「4096 能不能被引擎接受」，是 E2 的附带产出。

### 6.2 `3,597` 的来历（纠正口径）

- 直接出处：`glyphs.dat` 头部 `u32@0 = 3597`（14,392 = 4 + 3597×4，字节级吻合）；`p4_atlas_rebuild.py:25` 硬编码 `count = 3597`（遗留的旧重排路径，方案 A 已不采用）。
- `char_table_v2.dat` 是 3,596 条；`glyphs.dat` 去掉首项后与 v2 逐字同序 → 3597 = 3596 + 1，多出的正是 `0x0E0C`。
- **它不是物理图集容量**。物理：`128 × (4096/32) = 128 × 128 = 16,384`，末位 idx 16,383。
- 「余量 250 格」是**表记录余量**（3597 − 3347），不是贴图面积余量（贴图才用了 20.2%）。

### 6.3 两套坐标系换算（为什么不能在 512 口径上采样 4096 图集）

| 量 | 引擎假设（`0x9216BF` 支） | 我方图集 | 关系 |
|---|---|---|---|
| 列号 | `c_e = si & 0xF`（16 列） | `c_o = idx % 128` | `c_e = c_o & 0xF` |
| 行号 | `r_e = si >> 4` | `r_o = idx // 128` | `r_e = r_o*8 + (c_o >> 4)` |
| U 列距 | `1/16 = 32/512` | `1/128 = 32/4096` | 分母 ×8 |
| V 行距 | `40/512` | `32/4096` | `0.1 ×` |
| V 修正 | `+4/512 − 39.5/512` | 无 | 我方无此修正 |

**数值样例**（idx=379）：`c_o=123, r_o=2` → `U=3936/4096=0.9609375`，`V_top=64/4096=0.015625`，`V_bot=96/4096=0.0234375`。
同一 idx 按引擎 16 列解码：`c_e=11, r_e=23` → `U=0.6875`、第 23 行。**两者毫不相干。**
缺字「辖」`U+8F96`（若落在 idx=3597）：`c_o=13, r_o=28` → `U=416/4096=0.1015625`，`V=896/4096=0.21875`；引擎解码得 `c_e=13, r_e=224`，**越出 512 单页行范围** —— 这就是「不换算必错」的直接算术证据。

> 本轮实测结论：凡命中表里的字，`AdjustUV` **完全丢弃**引擎的 xmm4/xmm6/xmm7 并重算，UV 已验证正确（§1.3）。所以 §6.3 不是当前主因，而是**未命中那 376,688 次**（18.2%）的错位来源，以及方案 C 的必读章节。

### 6.4 容量预测（三档，模型与假设写清）

唯一锚点：P3 进度 33% 时非 ASCII 唯一字符 **3,347**（汉字 3,306 + 标点 41）。按「语料量 ∝ 进度」建模，`V = 3347 / 0.33^β`：

| 档 | 模型 | 算式 | 完成时 | 对表 3,597 | 对物理 16,384 |
|---|---|---|---|---|---|
| 保守 | Heaps β=0.5 | `3347 / 0.33^0.5` | **5,827** | 缺 2,230 | 余 10,557 |
| 中性 | Heaps β=0.55 | `3347 / 0.33^0.55` | **6,159** | 缺 2,562 | 余 10,225 |
| 上限 | Heaps β=0.6 | `3347 / 0.33^0.6` | **6,510** | 缺 2,913 | 余 9,874 |
| 稻草人 | 线性外推 | `3347 / 0.33` | 10,143 | 缺 6,546 | 余 6,241 |

**判断**：表 3,597 **不够**（保守档就差 2,230）；贴图 16,384 **够**（连稻草人上界都在内）。瓶颈是表上限，而表可追加。

> 口径提醒：3,347 是 P3 抽检值，与 final 表已收录的 3,309 不是同一快照，**不能相减当作新增余量**。33% 的分母口径（是否含三章、是否含 P4 队列）**未证实**，需在 P3 第二个进度点复核曲线后修正。

### 6.5 「只追加永不重排」的硬规则

1. **源头事实**：`glyph_map_final.tsv`（`index, codepoint, char, col, row, x, y`）。`char_table_*.dat` / `glyphs.dat` 都是派生物，只由表生成，**禁止手改**。
2. **HWM（high-water mark）**：初值 = 现 `glyphs.dat` max idx **3596**，下一个可用 idx = **3597**；新字一律 `HWM++`。
3. **永不复用空洞**。理由三层：(a) 旧图集/wtd 已把字形烘焙在那一格，位图改不掉；(b) 已提交的顶点、预烘焙缓存、外部存档可能仍按旧 idx 采样；(c) 同一 idx 在新旧图集里指向不同字形 → 混载必错字。删除只记账，不回收。
4. **预留块**：
   - A 段 `3,597 – 3,603`（7 格）：虱 `U+8671`、辖 `U+8F96`、啵 `U+5575`、钾 `U+94BE`、墩 `U+58A9`、瘆 `U+7606`、撬 `U+64AC`；
   - B 段 `3,604 – 6,158`（按中性档）：P3 剩余 67% 与 P4 的新字顺排；
   - 物理到 16,383 才触顶，中间还有 10,225 格缓冲。
5. **扩容不重排**：HWM 逼近 16,383 时换 8192²（格仍 32px → 256×256 = 65,536 槽），**只改 `font.cpp:16-18` 三个常量与图集尺寸**，`idx → (row,col)` 仍由 `idx % kCols` / `idx / kCols` 重算，`char→idx` 表**一行不动**。这就是「不重排」的定义：idx 身份永久不变，变的只是分辨率与网格常量。
6. **状态机（可回滚）**：读表定 HWM（只读）→ 过滤 `cp<0x100 || cp>0xFFFF`（与 `font.cpp:332` 一致）→ 逐字追加（幂等，已存在则跳过）→ 整批成功后由 TSV 重建 `glyphs.dat` → 任一步失败则丢弃本批尾行、HWM 回滚到进入前值。**以批为单位回滚，已冻结的旧行永不改写。**
