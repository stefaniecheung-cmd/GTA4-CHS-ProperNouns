## 一、旧补丁 `GTA4.CHS.asi` 的补丁点已完整提取

旧补丁不是硬编码地址，而是**特征码匹配**（CommonLibIV 的 batch_matcher）。
特征码表就在 asi 自己的 `.rdata`：

- `.rdata` 段：`va=0x10027000` `raw=0x25C00` `size=0xBE00`
- 特征码区：**`0x10027610` ~ `0x10028570`**，纯 ASCII，格式为 `XX XX ? ?`（`?`=单字节通配）
- 自动提取到 **61 条**，扫 `GTAIV.exe` 后 **52 条唯一命中**（9 条多命中或需二次判别）

提取脚本：`C:\Game\_tools\p4_sigscan.py`（可重跑）

### 命中点分布（按 RVA）

| 区域 | 命中点 | 性质判断 |
|---|---|---|
| `0x51B850` ~ `0x523819` | **约 30 个，主密集区** | **字体渲染核心**（度量、查表、绘制） |
| `0x1D5FE5` ~ `0x1E7B4B` | 8 个 | 字符串/字宽处理次群 |
| `0x12A7A` ~ `0x139C5` | 4 个 | UTF-8 解码路径 |
| `0x4B42B8` `0x4C97E1` `0x4CA0E7` `0x4CC4FF` `0x4C5FA1` | 5 个 | 文本/资源加载 |
| `0x78EDCD` ~ `0x78FE7C` | 4 个 | 文本输出 |
| `0x19F946` `0x2A3515` `0x3995D` `0x4D4CB0` `0x54EA6A` `0xBA60` `0x6132D4` | 各 1 | 杂项 |

**结论：引擎的字体渲染代码高度集中**，只要摸透 `0x51B800~0x524000`（约 35KB）这一片，取字链路就基本掌握。

## 二、已确认的引擎数据结构（这是自写 hook 的地基）

全部来自对命中点周边的反汇编，地址为**文件 RVA**（实际基址 = 0xC10000 + RVA-0x400000，即按模块基址+偏移取址，**不能写死**）。

### 2.1 字体记录：每字体 600 字节

```asm
0x91BD7C  movzx ecx, bl            ; bl = 字体索引
0x91BD7F  imul  ecx, ecx, 0x258    ; 0x258 = 600 = 每字体记录大小
0x91BD89  movzx eax, byte ptr [eax + ecx + 0x1195478]   ; 字宽表：每项 1 字节
0x91BD99  divss xmm0, dword ptr [ecx + 0x11956bc]       ; 除数
```

- **字体记录数组基址 `0x1195478`**，跨度 600 字节/字体
- 字体数量来源：`movzx eax, byte ptr [0x10366bd]`（早于 `0x91BD4B`）
- 字宽表是 **byte 数组**（`0x1195478 + font*600 + glyph_index`）
- 记录内已识别字段（基址 0x1195478 起算）：
  - `+0x200` = `0x1195678` float
  - `+0x204` = `0x119567c` float，被 `eax*4` 索引（**每字形 4 字节的宽度表**）
  - `+0x218` / `+0x21C` = `0x1195690` / `0x1195694` 校正值
  - `+0x228`~`+0x234` = `0x11956a0` / `a4` / `a8` / `ac` 四个字距范围端点
  - `+0x1C4` = `0x11956bc` 除数

### 2.2 字符属性表：每项 72 字节

```asm
0x91BDE3  call 0x91C150            ; 返回某索引 eax
0x91BDE8  lea  edx, [eax + eax*8]  ; eax*9
0x91BDEB  mov  cl,  byte ptr [edx*8 + 0x119bf40]   ; +0x00 = 行
0x91BDF2  movzx ebp, byte ptr [edx*8 + 0x119bf41]  ; +0x01 = 列
0x91BE05  imul eax, esi, 0x96      ; 0x96 = 150 = 列数
0x91BE07  cmp  byte ptr [edx*8 + 0x119bf2e], 0     ; 标志位
```

- `eax*9*8` = **72 字节/项**，基址 `0x119bf40`
- 字段：`+0x00` 行、`+0x01` 列、`+0x1C`/`+0x4C` float 偏移、`+0x2E`/`+0x30` 标志
- **图集布局常量：150 列（`0x96`）**，行数由行字段决定

### 2.3 kerning 表：word 项

```asm
0x91BD45  movzx eax, bl
0x91BD48  lea   ecx, [eax + eax*2]     ; font*3
0x91BD4B  movzx eax, byte ptr [0x10366bd]
0x91BD52  add   ecx, eax
0x91BD57  shl   ecx, 8                 ; *256
0x91BD5A  add   ecx, eax
0x91BD5C  movzx eax, word ptr [ecx*2 + 0x1193c78]   ; word 表
```

- 基址 `0x1193c78`，每项 word（u16）
- 索引算法：`((font*3 + byte[0x10366bd]) << 8) + char` —— 说明**按 256 字符一页分块**

### 2.4 全局状态字节（hook 时要读的开关）

| 地址 | 用途 |
|---|---|
| `0x10366bd` | 字体数量/当前字体索引基数 |
| `0x10366c1` | 第二字体索引 |
| `0x116c250` | 语言/字符集标志（`cmp ..., 0x6a` 特判） |
| `0x116c253` | 另一字符集标志 |
| `0x117e6da` | 开关字节 |
| `0x1036690` | 缩放除数 |

### 2.5 特判逻辑（重要）

多处出现 `cmp dx, 0x3f` / `cmp di, 0x3f` —— 即 **字符 `?`（0x3F）** 被单独处理（回退到 0xffff / 0xfd）。
说明引擎原本就会把「没有字形的字符」显示成 `?`。中文汉化后的「问号墙」正是走这条路径。

## 四、对「自写 hook」方案的三条硬结论

1. **字宽索引是 byte 宽度**（`movzx eax, byte ptr [...]`），原版单字体 600 个槽位 —— 这是我们要突破的第一个上限。
2. **图集是固定 150 列的网格**（`imul eax, esi, 0x96`），自建图集必须遵守这个列数，否则 UV 全错。
3. **所有地址必须按「模块基址 + RVA」取**，`GTAIV.exe` 带 ASLR（实测基址 `0xC10000`），写死绝对地址必失败。

## 五、【已破解】取字架构全貌

### 5.1 两级表结构（这是整个字形层的心脏）

**第一级：建表（启动/切字体时跑一次）**

`RVA 0x520380` 是填表循环：

```asm
0x00920369  mov  ebp, [esp+0x1c]        ; ebp = 字体索引 font（0..4）
0x0092036F  imul edi, edi, 0x600        ; 每字体 0x600 = 1536 字节
0x00920377  add  edi, 0x1193c78         ; 表基址
0x00920380  xor  esi, esi               ; esi = 页内字符 0..255
0x00920382  push ebx                    ; 参数3 page (0..2)
0x00920383  push ebp                    ; 参数2 font
0x00920384  push esi                    ; 参数1 char
0x00920385  call 0x91BAD0               ; ★★★ 字符 -> 字形槽位
0x0092038A  mov  word [edi], ax         ; 结果写 word
0x00920391  add  edi, 2
0x00920394  cmp  esi, 0x100             ; 256
0x009203A0  cmp  ebx, 3 ; jl            ; 3 页
0x009203CA  cmp  eax, 4 ; je             ; 5 个字体
```

→ **每字体 3 页 × 256 字符 = 768 个 word 槽位**，5 字体共 **3,840 槽位**
→ 表基址 `0x1193c78`，总长 5 × 1536 = 7,680 字节（运行时 BSS）

**第二级：查表（绘制时高频调用）**

```asm
0x91BD48  lea  ecx, [eax + eax*2]        ; font*3
0x91BD4B  movzx eax, byte ptr [0x10366bd]
0x91BD52  add  ecx, eax                  ; font*3 + X   (X = 页基址系数)
0x91BD57  shl  ecx, 8                    ; <<8
0x91BD5A  add  ecx, eax                  ; + char
0x91BD5C  movzx eax, word ptr [ecx*2 + 0x1193c78]   ; 取槽位号
```

### 5.2 `0x91BAD0` 完整逻辑（唯一映射入口，已逐条读通）

```asm
edx = [esp+4] + 0x20          ; char + 0x20
if (dx == 0x20)               ; 即 char == 0
     return 0xfd 或 0xffff    ; 视 [0x116c250]、[0x116c253] 决定
eax = [esp+0xc]               ; page
esi = [esp+0x10] * 0x258      ; font * 600
page==1 -> [esi+0x11956a0]..[esi+0x11956a4]   起,止
page==2 -> [esi+0x11956a8]..[esi+0x11956ac]   起,止
else    -> [esi+0x1195698]..[esi+0x119569c]   起,止

for (i = 起; i < 止; i++)
    if (byte[esi + i + 0x1195577] == char)     ; ★ 字符表：byte 数组
        return i                                ; i 就是字形槽位号
```

**爆炸性结论：**
- 引擎的「字符表」是 **`0x1195577 + font*600 + index` 的 byte 数组**，存的是**字符值本身**
- **下标 index 就是字形槽位号** —— 所以槽位与字符表位置绑定
- 字符值是 **byte（0~255）** → **原版引擎物理上无法表达 >255 的字符**
- 这就是「问号墙」的根本原因，也是旧补丁要改解码路径的根本原因

### 5.3 宽度表上限

```asm
0x91BD89  movzx eax, byte ptr [eax + ecx + 0x1195478]   ; ecx = font*600
```

- 宽度表：`0x1195478 + font*600 + slot`，**每项 1 字节**，slot 上限 599
- 所以要放 3,596 个字，**宽度表必须换成 4 字节 float 版**（引擎里已存在 float 宽度表 `0x119567c`，被 `eax*4` 索引）

### 5.4 旧补丁改的是解码路径，不是建表

sigscan 的 `.text+0x51BD89` 命中的正是宽度查表那条指令。
而 `0x10027FD4 / 0x10028008 / 0x1002803C / 0x10028070 / 0x10028098 / 0x100280D4` 这 6 条 sig 全部落在 UTF-8 解码段（`0x12A7A / 0x13311 / 0x13523 / 0x1E4CCE / 0x1E49DE / 0x1E5205`），
特征都是 `FF 8x 48 04 00 00` + `0F B6 5C 38 48` 这种「按 `+0x48` 偏移写缓冲」的模式。

→ **旧补丁的做法：在 UTF-8 解码阶段就把三字节中文序列转成槽位号，写进每字符 2 字节的缓冲，绕过 byte 字符表。**

## 六、【决定性】文本在引擎内部是 u16 数组

主遍历循环 `RVA 0x521948`：

```asm
0x921948  movzx eax, word ptr [edi]      ; ★ 读一个 u16 字符
0x92194D  test  ax, ax ; je  结束
0x921957  add   eax, -0x20               ; char -= 0x20
0x92195A  movzx edi, ax
0x921976  call  0x921140                 ; 绘制该字符（参数就是 u16 字符值）
0x921997  add   ebp, 2                   ; ★ 指针 +2，每字符 2 字节
0x9219A1  movzx eax, word ptr [ebp]      ; 下一个字符
0x9219A8  jne   0x921952
```

**这一条改变整个方案的设计：**

- 引擎内部文本 = **u16 数组**，每字符 2 字节，无 256 上限
- `0x921140(char, x, y, ...)` 是「绘制单个字符」，参数是 u16
- **唯一的 8 位瓶颈只在「char → 槽位」那次查表**（`(font*3+X)<<8 | char` 会把 >255 的字符污染）
- 上游（把 gxt/原文变成 u16 数组）才是 UTF-8 解码层，旧补丁改的就是那里

> 注意：绘制前有 `add eax, -0x20`，而 `0x91BAD0` 里又 `char + 0x20` 还原。
> **所以自建槽位号必须从 `0x20` 起编号**，否则会下溢成 0xFFxx。

## 七、方案 A 的改动清单（已收敛到极小）

### A-1 映射查表改为直通（解除 256 上限）

**位置 1**：`RVA 0x5215B5`（字符串测宽路径）
```asm
原: 0x9215B5  movzx esi, word ptr [edx*2 + 0x1193c78]   ; 6 字节
改: 0x9215B5  movzx esi, si                             ; 3 字节（0F B7 F6），余 3 字节 NOP
```
效果：`esi` 直接等于字符值 = 我们的槽位号。

**位置 2**：`0x91BC80` 函数内部的同款查表（`RVA 0x51BD5C`）
```asm
原: 0x91BD5C  movzx eax, word ptr [ecx*2 + 0x1193c78]
改:           movzx eax, dx                             ; dx = 字符
```

### A-2 宽度来源换成自建数组

`0x91BD89`：
```asm
原: 0x91BD89  movzx eax, byte ptr [eax + ecx + 0x1195478]   ; byte 表，slot ≤ 599
```
改为读取我们分配的 `uint16` 宽度数组（`width[slot]`），再 `cvtdq2ps` 后除除数。
**这条要重写 5~6 条指令，需要领地和跳板。**

### A-3 图集与 UV（沿用引擎）

- 图集 150 列网格不变（`imul eax, esi, 0x96`）
- 行号来自字符属性表 `0x119bf40`（72 字节/项）—— 但那是**排版配置**不是 UV
- 真正的 UV 在 `0x921140` 内部算，需再确认一次字段

### A-4 上游：把原文变成「槽位号 u16 数组」

这是唯一较重的活：
- gxt 里的字符串（我们打包的 `zchs_*.gxt`）在引擎读取后会被解码成一串 u16
- 需要在解码后、进入遍历前，把「Unicode 码点」换成「自建槽位号」
- 旧补丁是在 UTF-8 解码过程中直接完成替换（sig 落在 `0x12A7A / 0x13311 / 0x13523 / 0x1E4CCE / 0x1E49DE / 0x1E5205`）

**待确认**：这三处是不是同一个解码函数的三条分支，还是三个独立解码器（UI / 字幕 / 对话各一）。

## 八、本轮新增的三条实测修正

### 8-1 `0x921140`（绘制单字符）根本不查图集表

连续反汇编整个函数（0x921140–0x921533），全局表引用只有两个：

- `0x1195EB0`：字体缩放 float，`lea ecx,[eax*4 + 0x1195eb0]`，eax = `[0x10366c8]`（字体 ID）
- `0x11956B8`：字体记录 `+0x240` 的贴图指针，`push [eax+0x11956b8]` → `call 0x8d4cb0`（设纹理）

**没有 `0x119bf40`、没有 `0x119567c`、没有 `0x1193c78`。**

再往下 `0x8d3fd0` 把顶点数组与 UV 数组摊成 9 个 float 调 `0x8d3860`，其中 UV 部分是**固定的 0/0/0/1/1**。

→ **结论：字符的图集位置不是在这个函数里算的，而是靠绘制前设置的「纹理坐标变换矩阵」把某个格子映射成 0..1。** 设矩阵的地方才是 UV 的真源头。

### 8-2 `0x119BF40` 的项大小是 8 字节，不是 72

`0x91BDE8` 的 `lea edx,[eax+eax*8]` 后接 `[edx*8 + 0x119bf40]`，算出来是 `eax*72`；
但 `0x5243BD` 那一批是 `mov byte ptr [esi*8 + 0x119bf40], 0/1/3` —— **8 字节步长**。

两者都对，说明：**表项 8 字节，而 `0x91BDE0` 通过 `eax*9*8` 去读「第 0 项」或「第 9 项」**（eax 只会是 0/1，来自 `0x91C150` 的模式查询）。即它读的是两条固定的「图集条目配置」记录。

### 8-3 字符表可以在运行时被写入（重要机会）

`0x9207B5`：
```asm
0x9207A8  mov  ecx, ebx
0x9207AA  imul ecx, ecx, 0x258        ; font*600
0x9207B0  movzx eax, di               ; 槽位/字符
0x9207B3  lea  ecx, [ecx + 0x1195577] ; 字符表基址
```
后面紧接着就是往表里写值。

→ **引擎自己就有「设置某槽位字符」的路径**。这意味着自建映射不一定要在启动时一次性填满，可以按需懒填。

## 九、静态分析的极限（必须转入动态验证）

四张关键表全部在 `.data` 段的 **BSS 区**（文件里没有 raw 数据，运行时才填充）：

## 八、旧补丁被完整解密（运行时 .text diff）

这是本窗口的收官成果：**旧补丁 `GTA4.CHS.asi` 到底怎么接管取字，已经从内存里直接读出来了，不再靠推测。**

### 8-1 方法

1. 游戏到主菜单后 `p4_dump_text.py` 抓运行时 `.text` 全段（10,952,704 B）。
2. `p4_diff_text.py` 先解析 `.reloc`、按实测 `delta=0xBE0000` 对磁盘原版应用重定位，再逐字节 diff。
   **不先应用重定位会得到 349,994 字节"差异"（3.19%），全是 ASLR 噪声；处理后只剩 3,746 字节、768 个区间。**
3. `p4_scan_jumps.py` 全量扫 `.text` 里所有 `e8/e9`，按 `目标 = 模块基址 + RVA + 5 + rel32` 反算并归属模块。
   **注意：`rel32` 是相对 VA 的，必须加模块基址；漏掉基址会把 GTA4.CHS.asi 的 hook 全部误判成 DLSS-IV.asi。**

### 8-2 结论：旧补丁对 exe 代码只改了 15 处

全部归属 `GTA4.CHS.asi`（模块基址 0x6B750000）。其余"改动"属于 FusionFix / SISCO / DLSS-IV / mapfix / IVLodLights / AdvancedHookInit / XboxRainDroplets / ProceduralFixes。

### 8-3 关键：槽位空间是 0x20 ~ 0x3000

`+0x6660`（hook `0x521976`）开头就是决定性证据：

```asm
movzx esi, di          ; esi = 字符（u16）
add   esi, 0x20        ; ★ 槽位号 = char + 0x20
push  esi
call  +0x1D50          ; 查"该码位是否需要特殊处理"
cmp   esi, 0x3000      ; ★ 槽位上限 0x3000 = 12,288
je    <跳过>
```

**0x20 ~ 0x3000 = 12,256 个字形位置**，正好等于「4096² 图集切成 8×8 个 512² 页、每页 16 列 × 12 行 = 192 字」的 64 页 × 192 = 12,288。两条独立线索互相印证。

### 8-4 旧补丁的解码实现

9 个解码 thunk 都是同一模板（`pushal` / `add [esp+0xc],4` / `pushfd` / `call 实现` / `popfd` / `popal` / `ret`），实现函数在 `0x6B7594D0` ~ `0x6B759690`，形态一致：

```asm
mov  edi, [esp+0x10]        ; 文本对象
mov  ebx, [edi+0x1c]        ; 内部缓冲对象
lea  esi, [ebx+0x48]        ; 缓冲基址
add  esi, [ebx+0x448]       ; + 当前计数器
call 0x6B758EB0             ; 真正的转换（返回新位置）
mov  [edi+0x20], eax
sub  eax, esi
add  [ebx+0x448], eax       ; 计数器 += 实际写入长度
```

即：**把转换后的字节追加到 `[obj+0x48]` 起的缓冲，并更新 `[obj+0x448]` 计数器。** 计数器是字节数，写入长度由代码自己算，所以**每字符的字节宽度由补丁决定，不锁死在 1 字节**。

### 8-5 旧补丁自己重算了绘制坐标

`+0x6660` 在槽位判定之后有一大段浮点运算，例如：

```asm
movd     xmm0, ecx
cvtdq2pd xmm0, xmm0
addsd    xmm0, qword ptr [eax*8 + 0x6B777500]   ; 取整常量表
cvtpd2ps xmm0, xmm0
mulss    xmm0, dword ptr [0x6B7775F4]
mulss    xmm0, xmm3
movss    [esp+0x20], xmm0
```

即**它不走 exe 原有的 `0x9216C7` UV 段，而是在调用点之前自己把位置/UV 算好再交给绘制函数**。这就是为什么 `0x51B850` / `0x51BD89` / `0x51C150` / `0x5201E0` / `0x521140` 这些"命中点"在运行时 diff 里**全部未被改动** —— 那些 sig 只是定位锚点，补丁实际改的是它们的调用者/被调者。

### 8-6 对方案 A 的直接影响

1. **「A 方案只需要改代码，不需要改资源」这个前提是对的，但改动点不是 `0x9216C7`。** 真正要动的是 **`0x521976`** 这个绘制调用点（以及 `0x51C650`/`0x51C6C0` 两个度量入口）。
2. 旧补丁证明：**只要在 `0x521976` 前把「字符 → 槽位」和「槽位 → 位置/UV」都自己算好，就完全不用碰引擎原来的 UV 代码。**
3. 因此 A 方案的最小改动集是 **3 处**（`0x521976`、`0x51C650`、`0x51C6C0`），而不是原先设想的 4+ 处；解码层可以由我们自己的 `.gxt` 重定向路径在源头产出 u16 码点，未必需要在 `0x12A7A`~`0x1E5205` 这 9 处重复旧补丁的做法。
4. **槽位号必须落在 0x20 ~ 0x3000**，超界会被那段 `cmp esi, 0x3000` 判为无效。

## 九、UV 公式（静态常量已定死）

`0x9216C7` 起的换算（16 列分支，font0/1/3 走这里）：

```
列 = slot & 0xF                  → U 步进 = 列 × 0.0625 (1/16)
行 = slot >> 4
页高 512.0（字体记录 +0x248 = 0x11956C0）
行高 40.0（+0x24C）、留白 4.0（+0x250）、行底 39.5（+0x254）
V 步进 = 行高 / 页高 = 40/512 = 0.078125
```

常量实名值（`.rdata` 实测）：`0xE85F54`=0.0025（slot≥192 基值）、`0xE85F58`=0.0048（slot<192 基值）、`0xE85F60`=0.02001953、`0xE85F64`=0.02040816、`0xE85F68`=0.045、`0xE85F74`=41.0、`0xFE8778`=0.0625、`0xFE88E8`=1.0、`0xFE86B4`=0.001、`0xFE86A0`=0.00048828、`0xFE8628`=0.0、`0xFE8D1C`=-0.0、`0xFE8CF8`=8388608.0。

**font2 走 49 列分支**（`idiv 0x31`）：U 步进 1/49 = 0.02040816，行步进 41/2048；font2 的字体记录字段全为 0（当前未启用）。

## 十、运行环境中已确认的字体数据（主菜单快照）

映射 word 表 `0x1193C78`，每字体 0x600 = 768 word，**只有 4 个有效**（font0/1/3；font2 全零未用；`0x1195478` 是字体记录起点，不是第 5 张映射表）。映射值上限 **0xFD = 253**，唯一值 165~202 —— 即每字体实际字形远少于 768。

字体记录 `0x1195478`，每字体 0x258 = 600 B：`+0x00` 字宽 byte 表、`+0xFF` 字符 byte 表（线性搜索）、`+0x240` 贴图指针、`+0x248` 页高 512.0、`+0x24C` 行高 40.0、`+0x250` 留白 4.0、`+0x254` 行底 39.5。

字符表实测从 ASCII `!"#$%&'()*+,-./01…` 起，印证「字符表是 byte 数组、值域 0~255」——这正是"问号墙"的物理原因。
