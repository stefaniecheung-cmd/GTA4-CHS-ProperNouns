## 1. 入口与初始化

### 1.1 DllMain 链与线程模型

【实测】入口 RVA `0x1DDB8` → CRT 调度 `0x1DA6B`；attach 路径经 CRT DLL 包装 `0x1DABE`（SEH_prolog4），detach 路径 `0x1DBC8`。`0x1DABE` 内依次 `___scrt_initialize_crt` → `initterm_e(0x271D0, 0x271D8)` → `initterm(0x271A4, 0x271C4)`，执行 CRT 静态初始化槽：`0x271AC→0x10001100`、`0x271B4→0x100010DC`、`0x271BC→0x10001000`。

【实测】**未导入 `CreateThread` / `CreateRemoteThread`**（导入清单仅 KERNEL32 42 + msvcrt 59，见 `01-静态结构.md` §1.3）。初始化在 DllMain attach 上下文内联完成，运行在 loader-lock 中；没有延迟到独立工作线程。

### 1.2 真正的补丁初始化 `0xC700`

【实测】用户侧初始化包装 `0x5F40`（`__stdcall`，`ret 0xC`）先判 reason==1，再把 HMODULE 压栈、`ECX = 0x10037A48`（全局补丁管理器对象），调用主初始化 `0xC700`（`__thiscall`，`ECX=this`）：

```
; 0x10005F40  反汇编（capstone）
0x10005F40  cmp  dword ptr [esp+8], 1      ; reason
0x10005F45  jne  0x10005F5B
0x10005F47  push dword ptr [esp+4]        ; hModule
0x10005F4B  mov  ecx, 0x10037A48          ; 管理器对象
0x10005F50  call 0x1000C700              ; 主初始化
0x10005F55  movzx eax, al
0x10005F58  ret  0xC
```

【实测】`0xC700` 流程（伪代码，依据 `asi_dump3.txt` 中 `0xC700` 伪代码）：

```c
// RVA 0xC700  __thiscall，ECX=this；栈上传 HMODULE
void PatchManager::init(this, HMODULE asiMod)
{
    GetModuleHandleW(NULL)            // 游戏 exe 模块
    -> 0x2990 存入 this+0x00          // 解析模块路径目录
    asiMod -> 0x2990 存入 this+0x1C;

    // 注册各子系统签名组：0x7650/0x7D50/0x83F0/0x8B70/0x96C0/0x9F40/0xA0E0/0xA2A0/0xC110
    0x3FD0();                         // 扫描：遍历签名记录链表，匹配地址存 record+0x50
    0x3F20();                         // 校验 + 安装 hook
    0x4230();
    0x8620();                         // exe 内特征段改写（见 §3.6）

    // 资源加载（fopen/_wfsopen/fread）
    char_table.dat  -> this+0x38;
    whm_table.dat   -> this+0x44;
    custom_translations.json -> 0x14D00;
}
```

【实测】模块路径解析 `0x2990`（`__thiscall`，2 参）：`GetModuleFileNameW(hModule, buf, 0x200)`，按 `\` / `/` 切分目录，模块 HMODULE 与目录分别存 `this+0x00` / `this+0x1C`。数据表文件名取自 `.rdata`：`char_table.dat`(RVA `0x2859C`)、`whm_table.dat`(`0x285AC`)、`custom_translations.json`(`0x285BC`)、`font_chs`(`0x275C8`)。

【未确定】`0x5F40` 作为用户 DllMain 回调被 CRT 调度槽引用的确切数据槽位置，静态未追溯到固定 RVA（`.text` 内无指向 `0x5F40` 的 rel32 call，也无绝对指针落盘）；依据是对 asi 全量做了绝对双字扫描，`0x10005F40` 零命中。不影响「attach 内联初始化、无独立线程」的结论。

## 2. Hook 安装机制

### 2.1 总体判定：inline hook，未见 IAT hook / vtable 替换

【实测】所有安装路径最终都改写游戏 `.text` 目标处的指令字节（`E8` call rel32 或 `E9` jmp rel32），由 `VirtualProtect` 包裹改写。证据：
- 导入表无游戏模块 IAT 相关操作；安装器核心 `0x7110`/`0x7680` 直接对目标指针写操作码字节（§2.3）。
- 全文件未发现对游戏 vtable 指针表的批量写；RTTI 命名空间（`gta_font`/`gta_game`/`gta_menu`/…）下的 `register_patches(batch_matching&)` lambda 只是签名记录注册器，不是函数指针替换。

【实测】定位手段：**字节特征码（signature scan）+ 出现序号 + 结果槽**，不是硬编码 exe VA。登记函数 `0x40E0`（`__thiscall`，4 参：this、hex 模式串、出现序号、结果槽 `.data`）；扫描 `0x3FD0`（`__fastcall`）遍历记录链表，解析出的匹配绝对地址写 `record+0x50`；校验/安装 `0x3F20`（`__fastcall`）。

```c
// RVA 0x40E0  __thiscall(this, const char* sigHex, int occurrence, void* resultSlot)
void Matcher::register(this, sig, occurrence, resultSlot)
{
    // 把 hex 模式（'?' 通配）+ 序号 + 结果槽挂入记录链表
    FUN_100035E0(this, local_rec, &sig, wildcard);
}
```

【实测】版本锁定证据：`.rdata` 字符串 `1.2.0.59 sub_91EE50`（raw `0x269E0`）紧随三条特征 hex：`8B F8 8D 44 24 08 50 57 E8`、`74 0A 50 55 E8`、`7F 4B 56 52 8D 44 24 14 50 E8`。`0x91EE50` 是日志里记录的被匹配 exe 目标地址（exe VA 量级）。

### 2.2 安装点统计（capstone 全 `.text` 扫描 call 目标）

| 安装器 | 改写指令 | 调用点数（call 到安装器） | 证据 |
|---|---|---|---|
| `0x7110` | `E8` call rel32 | 57 处 | `call_scan.py` 输出；其中 `0x6CB0` 批量占 20 处 |
| `0x7680` | `E9` jmp rel32 | 3 处（`0x79A0`、`0x79CD`、`0x7B9D`） | 同上 |

【实测】批量安装器 `0x6CB0`（`__stdcall`，1 参）一次挂 20 个 call-site，handler 统一为 `0xBAD0`；目标 = 签名解析出的基址指针 + 偏移，偏移清单：`0x4D3/0x920/0x95C/0x998/0x9D4/0xA10/0xA4C/0xA88/0xAC4/0xB00/0x13BC/0x14BC/0x19D7/0x1A21/0x1A74/0x1AB0/0x1AEC/0x1B28/0x1B5D/0x203B`。

```c
// RVA 0x6CB0  伪代码（asi_dump2.txt 2816 行起）
void Batch::install(this)
{
    FUN_10007110(&out, *(int*)*this + 0x4D3,  0x1000BAD0, 1);
    FUN_10007110(&out, *(int*)*this + 0x920,  0x1000BAD0, 1);

```

【未确定】上表偏移相对的是签名记录解析出的基址对象（`*(int*)*this`），静态未逐一换算成 exe RVA；各 hook 在运行时落到 exe `.text` 的最终 VA 由 `0x3FD0` 扫描结果决定，本节不逐一列出 exe 侧 RVA。单个 handler 与游戏原函数约定的精确匹配关系，部分未逐一核实（§4）。

### 2.3 安装器 A `0x7110`（写 `E8` call rel32）

【实测】签名：`__cdecl`，4 个栈参 `(out_orig*, target, new_handler, length)`。流程：
1. `VirtualProtect(target, len, 0x40/*RWX*/, &old)` 改可写；
2. 读目标处现有指令并分类：`0xE8` call rel32 / `0xE9` jmp rel32 → 交 `0x7450` 解析出原始绝对目标写入 `*out_orig`；`0xFF` 且次字节 `0x15`(call [mem]) / `0x25`(jmp [mem]) → 解引用内存指针；否则 `*out_orig = 0`；
3. 改写：`*target = 0xE8`，由 `0x72D0` 写 rel32 位移 `disp = handler - (field+4)`，操作数宽 4；
4. 再次 `VirtualProtect` 恢复原页属性。

```c
// RVA 0x7110  伪代码（依据 asi_dump2.txt / asi_dump3.txt 0x7110 反编译）
int __cdecl InstallCallHook(void* out_orig, void* target, void* handler, uint len)
{
    DWORD old;
    VirtualProtect(target, len, 0x40, &old);
    uint8 op = *(uint8*)target;
    if (op == 0xE8 || op == 0xE9)
        *out_orig = ResolveRel(op, target);        // 0x7450: rel8/16/32 → 绝对地址
    else if (op == 0xFF && (next == 0x15 || next == 0x25))
        *out_orig = *(void**)(target + 2);         // FF15/FF25 解引用
    else
        *out_orig = 0;

    *(uint8*)target = 0xE8;                        // call rel32
    RelocateWriter(target + 1, handler, 4, len);    // 0x72D0
    VirtualProtect(target, len, old, &old);
}
```

### 2.4 安装器 B `0x7680`（写 `E9` jmp rel32）

【实测】签名：`__cdecl`，4 栈参。先由 `0x6FD0` 读原指令并解析原目标，再写 `0xE9`，位移仍交 `0x72D0` 重定位；`VirtualProtect` 同样 RWX → 写 → 恢复。

```c
// RVA 0x7680  伪代码（asi_dump3.txt 2052 行起）
undefined4* __cdecl InstallJumpHook(out_orig, target, handler, uint len)
{
    FUN_10006FD0(out_orig, target, len);           // 读原指令、解析原目标
    if ((len & 0xFF) == 0) {
        *(uint8*)target = 0xE9;
    } else {
        BOOL ok = VirtualProtect(target, len & 0xFF, 0x40, &old);
        *(uint8*)target = 0xE9;
        if (ok) VirtualProtect(target, len & 0xFF, old, &old2);
    }
    FUN_100072D0((int*)(target + 1), handler, (int*)4, bWild);  // rel32 重定位
    return out_orig;
}
```

### 2.5 辅助例程与 trampoline 判定

| RVA | 约定 | 职责 |
|---|---|---|
| `0x7450` | `__cdecl` | rel8/rel16/rel32 → 绝对地址：`target = field_addr + disp + instr_len` |
| `0x72D0` | `__cdecl` | 重定位写入器（`VirtualProtect` 包裹，支持 rel8/16/32） |
| `0x6FD0` | `__cdecl` | 读目标处现有 call/jmp 并解析目标 |
| `0x6C40` | `__cdecl` | 次字节读取，判定 `0x15` / `0x25` |
| `0x8090` | `__stdcall`，1 参 | handler 侧解析被 hook 目标的原始绝对目标，存全局 `DAT_10037B20` |

【实测】**没有分配跳板（trampoline）内存**：导入表无 `VirtualAlloc` / `VirtualAllocEx`，也未发现被覆盖指令字节的拷贝。原始目标以**绝对指针**形式保存在 out_orig 结构 / 全局 `DAT_10037B20`；handler 需要调原函数时，经保存的指针回跳。

【实测】**相对跳转 / 相对 call 的地址重定位已处理**：`0x7450` 把原 rel 偏移解析成绝对地址保存；`0x72D0` 按新 handler 位置重算 rel32。但**未做按指令长度的反汇编指令拷贝**（无解码器、无被覆盖字节搬迁）——被覆盖的若干字节不会被搬到跳板执行，这是该实现与标准 detour 跳板的关键差别。

【实测】改写覆盖长度：两种安装器写出的都是 **5 字节**（1 字节操作码 `E8`/`E9` + 4 字节 rel32）。`length` 入参只用于 `VirtualProtect` 的页保护区域大小与指令分类，不决定拷贝长度。

### 2.6 另一处 exe 内改写 `0x8620`

【实测】`0x8620`（`__stdcall`，0 参，410B）在 exe 内存中扫描 `.text` 特征段，定位唯一匹配后把 9 字节 `0xCC` 改写为 `DAT_10027DB4` 起的字节，再把 1 字节写成 `'6'`(`0x36`)。

【未确定】该改写的确切语义（版本校验绕过 / 崩溃检查绕过 / 反调试绕过）未完全确认；证据仅到「按特征定位 + 静态字节补丁 + 改一个字符为 `0x36`」，缺运行时行为对照。

## 3. 调用约定与栈平衡

### 3.1 各核心例程约定（Ghidra 推断 + 反汇编 `ret n` 核验）

| RVA | 约定 | 参数来源 | 栈平衡归属 |
|---|---|---|---|
| `0x7110` 安装器 A | `__cdecl` | 栈 | 调用方清栈（调用后 `ADD ESP,0x10`） |
| `0x7680` 安装器 B | `__cdecl` | 栈 | 调用方清栈（`ADD ESP,0x10`） |
| `0x72D0` / `0x7450` / `0x6FD0` / `0x6C40` | `__cdecl` | 栈 | 调用方清栈 |
| `0x8090` 原目标解析 | `__stdcall`，1 参 | 栈 | 被调方 `ret 0x4` |
| `0x40E0` 签名登记 | `__thiscall` | `ECX=this` + 栈 | 调用方清栈 |
| `0x3FD0` 扫描 / `0x3F20` 校验安装 | `__fastcall` | `ECX`/`EDX` + 栈 | 按 `__fastcall` |
| `0xC700` 主初始化 | `__thiscall` | `ECX=this` + 栈 | 调用方清栈 |
| `0x2990` 模块路径 | `__thiscall` | `ECX=this` + 栈 | 调用方清栈 |
| `0xBAD0` UTF-16→UTF-8 | `__cdecl`，2 参 `(ushort* src, byte* dst)` | 栈 | 调用方清栈（`ADD ESP,8`） |
| `0x6210` 宽度计算 | `__cdecl`，3 参，返回 `float10` | 栈 | 调用方清栈 |
| `0x6660` 字形绘制 | `__cdecl`，4 参 `(float x, float y, uint char, param4)` | 栈（XMM/浮点栈返回） | 调用方清栈 |
| `0x1FCE0` 格式解析 | `__fastcall`，1 参 | `ECX`/栈 | 按 `__fastcall` |

### 3.2 handler 约定与裸函数判定

【实测】注册为补丁 lambda / 包装器的例程多为 `__stdcall` params=1（`ret 4`）；`0x77E0–0x78B0` 区间是 13 字节 `__stdcall` 桩。**未发现 naked / 裸函数或手写内联汇编 thunk**：所有被列函数都有标准 prologue（`push ebp / mov ebp,esp` 或 `sub esp,…`）与 epilogue，handler 参数按被 hook 游戏函数的原约定从栈 / `ECX` / `EDX` 取。

【未确定】逐个 hook handler 与游戏原函数约定是否逐字匹配（尤其是 `__thiscall` 的 `ECX=this` 回填与浮点返回值），静态只核验了 asi 侧函数自身的约定；运行时栈不平衡会以崩溃表现，本节未做动态验证。

### 3.3 返回值回填

【实测】`__cdecl` 宽度函数 `0x6210` 经浮点栈 / `XMM0` 返回宽度；绘制函数 `0x6660` 计算四边形坐标后交 `0x6BD0` 画 quad，自身无显式整数返回。`0xBAD0` 返回指向输出 UTF-8 缓冲末尾的指针（`param_2` 递增后写 `0`）。

## 4. 异常与崩溃保护

### 4.1 未使用的保护机制

【实测】导入表**无** `AddVectoredExceptionHandler`（VEH）、**无** `IsBadReadPtr` / `IsBadWritePtr`、**无** `SetUnhandledExceptionFilter` 之外的顶层异常链注册。`IsDebuggerPresent` 仅用于状态判断，不是崩溃守护。

### 4.2 实际存在的异常 / 安全机制

【实测】复杂函数内存在编译器生成的 C++ SEH 帧：prolog 内 `push fs:[0]` 链（`ExceptionList`）、`__security_check_cookie` 栈 Cookie（`DAT_10033100 ^ EBP/ESP`），处理件走 `__CxxFrameHandler3` / `_except_handler4_common`；C++ 异常经 `_CxxThrowException` 抛出（如 `0xBAD0` 遇非法代理对 / 越界码点时抛异常，ThrowInfo `DAT_10030FA0` / `DAT_10030F48`）。

【实测】`SetUnhandledExceptionFilter` / `UnhandledExceptionFilter` 只出现在 CRT 崩溃上报路径：`0x1E4D7`（RTC 失败 `0x40000015`）、`0x1EA50`（栈缓冲溢出 `0xC0000417`）、`0x1E2C7`。**这是 CRT 自身的未处理异常上报，不是补丁层安装的自定义顶层崩溃守护**。

【实测】hook handler 周围未识别到自定义 `__try/__except` 帧； asi 侧主动做的内存访问边界判断仅在查表 / 编码函数内部（如 `0xBAD0` 的代理对与码点范围检查），没有对游戏只读指针做批量 `IsBadReadPtr` 探测。

## 5. 文本链路接管层次

链路按「key→string 查询 → 排版 / 换行 / 宽度 → 字形绘制」三层归类，证据如下。

### 5.1 查询 / 编码 / 格式层

| RVA | 约定 | 职责 | 证据 |
|---|---|---|---|
| `0x5CE0` | `__cdecl`，2 参 | 按 key 查表（表 / JSON）取译文；未命中返回默认串（`.rdata 0x100275B4` 起） | `asi_dump3.txt` `0x5CE0` 反汇编：先调 `0x1CB1E` 查表，空结果走默认串回填 |
| `0xBAD0` | `__cdecl`，2 参 | UTF-16 → UTF-8 编码器；解码代理对，非法字符 `_CxxThrowException`；逐字交 `0x8C50` | 伪代码见 §2.3 引述，`asi_dump3.txt` 145 行起 |
| `0x8C50` | — | 逐字 UTF-8 编码 | 被 `0xBAD0` 调用 |
| `0x1FCE0` | `__fastcall`，1 参，1264B | printf 风格格式符解析（`%A/%E/%F/%G/%C/%S/%X/%Z…`），用 `wctomb_s` / `wcsnlen` / `strnlen` | `asi_dump3.txt` 1033 行起，`switch` 按格式符分派 |

【未确定】**key→string 的 GXT 查询层本身是否被 hook，未见直接证据**。`0x5CE0` 是 asi 自己的译文查表入口；它挂在游戏文本链的哪个 call-site 上、是否替换了游戏原本的 GXT key 查询返回值，静态未定位到对应的 exe 目标（§6 对照也未发现对 exe 查询函数的直接引用）。

### 5.2 宽度 / 排版层

| RVA | 约定 | 职责 | 证据 |

## 8. 机制层关键结论

1. **初始化无独立线程**：DllMain attach 内联完成（无 `CreateThread`），在 loader-lock 上下文里取模块、扫签名、装 hook、读外置表；attach 包装 `0x1DABE`，主初始化 `0xC700`（经 `0x5F40` 调用）。
2. **hook 类型是 inline hook**：改写游戏 `.text` 目标为 `E8` call rel32（安装器 `0x7110`，57 处）或 `E9` jmp rel32（安装器 `0x7680`，3 处）；未见 IAT hook、未见 vtable / 函数指针批量替换。
3. **定位靠签名扫描，不靠硬编码 exe VA**：`0x40E0` 登记模式 / 序号 / 结果槽，`0x3FD0` 扫描，`0x3F20` 校验安装；版本锁定 1.2.0.59（字符串 `1.2.0.59 sub_91EE50` + 特征 hex）。
4. **没有标准 detour 跳板**：无 `VirtualAlloc`，不拷贝被覆盖指令；原始目标以绝对指针存 out_orig / 全局 `DAT_10037B20`，handler 经保存指针回跳；相对 call/jmp 的重定位由 `0x7450`/`0x72D0` 处理，但不做指令长度反汇编搬迁。
5. **写保护走 `VirtualProtect` RWX 包裹再恢复**：`0x7110`/`0x7680`/`0x72D0`/`0x8090` 均为「改页保护 → 写 → 恢复原属性」；每次写出 5 字节（1 操作码 + 4 rel32）。
6. **约定混用、无裸函数**：安装器核心 `__cdecl`（调用方清栈）；注册桩多为 `__stdcall`；管理器 / 查表为 `__thiscall`/`__fastcall`；未发现 naked thunk；hook handler 约定跟随被 hook 的游戏函数，逐项匹配关系部分未核实。
7. **异常保护薄弱，无 VEH、无 IsBadReadPtr 探测**：仅有编译器生成的 C++ SEH 帧与栈 Cookie；`SetUnhandledExceptionFilter` 只服务 CRT 崩溃上报，不是补丁层自定义守护；非法码点以 C++ 异常 `_CxxThrowException` 抛出。
8. **接管落在宽度计算 + 字形绘制 + 编码格式层，绕开 GXT**：译文 / 字宽 / 字形来自自带 `char_table.dat`、`whm_table.dat`、`custom_translations.json`；对 exe `0x8C5DF0/0x8C6780/0x8C5CC0/0x8C5D70` 零直接引用，无 `.GXT` / `TABL/TKEY/TDAT` / `common:/text` / `update\` 痕迹；key→string 查询层是否被间接接管，未见直接证据，列为未确定项。

| 串比较循环 | `0xA020` | `0xB510` | 1 |
| **哈希查表取串（见 9.3 / 9.4）** | `0xA190`、`0xA220` | `0xB6A0` | 2 |
| **哈希查表取串（见 9.3 / 9.4）** | `0xA1C1`、`0xA1E8` | `0xB3C0` | 2 |
| UTF-16→ANSI 逐字转换 | `0xA250` | `0xBBF0` | 1 |
| pushal 包装 | `0xC0CA` | `0xC020`（→`0xC0F0`） | 1 |

合计 `E8` 调用点 57、`E9` 调用点 3（`0x79A0`、`0x79CD`、`0x7B9D`），与 §2.2 统计一致。

**为什么静态给不出 exe 目标 RVA：** 批量安装器 `0x6CB0` 内目标 = 签名记录解析出的基址对象 + 小偏移（偏移清单见 §2.2）；单个安装点同理。exe 侧最终 VA 要等运行时 `0x3FD0` 签名扫描回填到记录 `+0x50` 槽，静态 asi 镜像里只有特征 hex 与结果槽，没有 exe 绝对地址。

**E8 call hook 与 E9 jmp hook 的用途差异、返回值回填与回跳：**

- **E8 call rel32（安装器 `0x7110`，57 处）**：目标处改写为 `E8 handler`。游戏流程到达目标时执行 `call`，**压入返回地址 `target+5`** 进栈，再跳入 handler；handler `ret` 后回到原调用点后续指令。原目标函数体默认不被进入；handler 需要调原函数时，经安装期解析保存的原始目标指针回跳。返回值按原函数约定经寄存器 / 浮点栈回填到调用方。
- **E9 jmp rel32（安装器 `0x7680`，3 处）**：目标处改写为 `E9 handler`，**无条件跳转、不压返回地址**。handler 不能靠 `ret` 自动回到 `target+5`；要么完全接管原函数职责，要么经保存的原目标指针自行重新调用原函数后再返回。
- **回跳通路**：全局 `DAT_10037B20` / `DAT_10037B24` 在安装期由 `0x8090` 解析写入原始目标；回跳桩 `0x77D0` 反汇编：

```
; RVA 0x77D0（capstone）
0x100077D0  pop  edi                     ; 取回跳转地址
0x100077D1  call dword[0x10037B24]      ; 调保存的原函数
0x100077D7  or   eax,0x80000000         ; 返回值置标志位
0x100077DC  jmp  edi                    ; 跳回调用点
```

  `0x77B0` / `0x77C0` 是标志 / 指针规整桩（`and edi,0x7FFFFFFF` 后取字 / 写字节），不是原函数调用。
- **栈平衡归属**：安装器自身 `__cdecl`，调用方清栈；各 handler 约定跟随被 hook 的游戏函数（§3.1）。逐个 handler 与游戏原型的逐字匹配仍属未确定项（需动态 / 对照 exe 原函数原型）。

### 9.3 裁决三：是否「两段式」——UI / 短串在 asi 侧哈希查表换中文，剧情长文本靠外部已汉化 gxt 走游戏链路

**裁决：两段式成立。** 证据链覆盖 asi 二进制内的短串查表路径；「长文本走替换后的 gxt」是部署包层事实（`03-字体与生态.md` §覆盖清单），asi 二进制内**未发现**任何接管 GXT 查询 / 解析的代码（§6 已证）。

**第一段（asi 内，UI / 短串 / 菜单 / 电话 / 邮件 / 提示类）：** 串进入下游排版 / 绘制前，在 asi 侧按 FNV 哈希查 `whm_table.dat` 串池换中文；未命中则透传原文。

| 环节 | RVA | 职责（证据） |
|---|---|---|
| whm 串池装载 | `0x1BBE0` | `__thiscall`，从 `0xC8F0` 调用（`xref2.py` caller 列表）；把 `whm_table.dat` 头表 + NUL 分隔 UTF-8 串池载入全局对象 |
| char_table 装载 | `0x58D0` | 从 `0xC8A2` 调用；载入 3,580 个允许 Unicode 码位 |
| 码位二分成员判定 | `0x5850` | 被 `0x58C2`（装载期）与 `0x6717`（绘制路径）调用 |
| JSON 覆盖查表 | `0x5CE0` → `0x1CB1E` | `custom_translations.json` 取值；未命中回填默认串（`.rdata 0x100275B4`）；`0x1CB1E` 由 `0x5D14` 调用 |
| 运行期哈希查表 handler | `0xB6A0`、`0xB3C0` | 见下方反汇编；各挂 2 个安装点 |
| 哈希表桶链查询 | `0xA560` | 桶数组 + 链表节点比对 `node+8` 键；返回命中节点或哨兵 `0x10037A2C` |
| 未命中透传拷贝 | `0xA330` | ANSI→UTF-16 逐字展宽拷贝原文（`punpcklbw`） |
| 排除表成员判定 | `0x1CCA2` → `0x1CCD5` | 查全局排除表 `0x10033058`，`strcmp` 式比对 |
| 引用计数释放 | `0x1CCB3` | 查表后 `[ecx+0x2C]--`，归零释放 |

**查表键与哈希算法（已还原）：FNV-1a 32 位。** 常量证据（`0xB6A0` / `0xB3C0` 内联，`dis_lookup.txt`）：

```
; RVA 0xB6A0（capstone，哈希主体）
0x1000B6F9  add  edi,esi                ; 串尾 = 首址 + 长度
0x1000B6FB  mov  edx,0x811C9DC5         ; FNV offset basis
0x1000B704  movzx eax,byte[esi]
0x1000B707  inc  esi
0x1000B708  xor  eax,edx
0x1000B70A  imul edx,eax,0x01000193    ; FNV prime
0x1000B710  cmp  esi,edi
0x1000B712  jne  0x1000B704
; 随后对哈希值自身 4 字节再做一轮混合（shr 8/0x10/0x18），
; 并与全局 salt 0x10037A28 组合，交 0xA560 查桶链
0x1000B749  mov  ecx,0x10037A28        ; 哈希表对象 / salt
0x1000B756  push eax                   ; 最终哈希键
0x1000B761  call 0x1000A560            ; 桶链查询
```

- **键**：英文源串的 ANSI / ASCII 字节序列（长度由 NUL 扫描得到，逐字节参与哈希）；basis `0x811C9DC5`、prime `0x01000193` 均为标准 FNV-1a 32 常量。
- **二次混合**：首轮 FNV 之后，代码再把 `edx` 的四个字节经 `shr 8 / 0x10 / 0x18` 逐字节喂回同一 prime 做 finalization，并叠加全局 `0x10037A28`；这是在标准 FNV-1a 之上的附加混淆，确切 finalization 语义以反汇编为准。
- 同类 FNV 查表助手还存在于 `0xA63A`、`0xFACA`、`0x14CD0` 所在函数；`0xA7AA`、`0xFC02` 所在函数是哈希表**装载期插入**路径（链表链指针维护）。

**命中 / 未命中走向（`0xB6A0`，`0xB3C0` 同构）：**

```c
// RVA 0xB6A0 / 0xB3C0  伪代码（依据 dis_lookup.txt）
void LookupTranslate(src /*[esp+0x18/0x1C]*/, dst /*[esp+0x20/0x1C]*/)
{
    if (!src || !dst) return;
    len = strlen(src);
    if (InExcludeList(0x10033058, src, len))   // 0x1CCA2
        Abort(5);                                // 0x1CE51(5)，不参与翻译
    if (DAT_10033084 == 0x7FFFFFFF) { Abort(6); DAT_10033084=0x7FFFFFFE; }

    h = FNV1a_32(src, len) + finalize + salt;   // 0x811C9DC5 / 0x01000193
    node = HashMapLookup(0x10037A28, h);       // 0xA560
    if (node != sentinel 0x10037A2C) {
        memcpy(dst, node+0xC, node+0x10 - node+0xC);  // 命中：拷译文区间
        ReleaseRef(0x10033058);                  // 0x1CCB3
    } else {
        PassthroughWiden(dst, src);               // 0xA330：未命中透传原文
        dst[0] = 0;                              // 写终止符
        ReleaseRef(0x10033058);
    }
}
```

- **命中**：节点 `+0xC` / `+0x10` 给出译文串起止区间，经 `0x1E876`（memcpy）拷入输出缓冲；译文来自 `whm_table.dat` 串池。
- **未命中**：`0xA330` 把原文逐字节展宽拷贝进输出缓冲（保持英文原样），写 NUL 终止符。
- **前置过滤**：命中排除表 `0x10033058` 或守卫 `0x10033084` 异常时走 `0x1CE51` 编号中止路径（消息表 `0x1002C9B0` / 类别表 `0x1002C9CC`），不是静默透传。

**第二段（外部部署层，剧情 / 长文本）：** asi 自身不读 `.gxt`、不解析 `TABL/TKEY/TDAT`、无 `common:/text` / `update\` 路径串（§6.1）；剧情长文本依赖附属补丁替换的三章 `american.gxt`，由游戏自带 GXT 链路（`0x8C5CC0` 基路径 → `0x8C5D70` 拼路径 → `0x8C6780` 解析 → `0x8C5DF0` 选语言名）加载，asi 不接管这一层。该段的 gxt 替换清单属部署包事实（见 `03-字体与生态.md`），在 asi 二进制内不可见。

### 9.4 裁决四：key→string 查询层到底有没有被 hook

**三态结论：**

| 子结论 | 状态 | 依据 |
|---|---|---|
| asi 侧「取串 / 串包装」入口被 hook，在宽度 / 绘制前按哈希换中文 | **已证实** | 4 个安装点 handler `0xB6A0`（`0xA190`、`0xA220`）、`0xB3C0`（`0xA1C1`、`0xA1E8`），内部 FNV-1a 查表 + 命中拷译文 / 未命中透传（9.3 反汇编）；`hook_map.py` 直接映射到上述 handler |
| exe 原生 GXT key 解析 / 查询函数被 hook | **已排除** | 对 `0x8C5DF0` / `0x8C6780` / `0x8C5CC0` / `0x8C5D70` 的 VA 与 RVA 打包双字扫描零命中；asi 内无 GXT magic / 路径串（§6.1、§6.2） |
| 被 hook 的 4 个入口对应 exe 侧哪个原生函数（原型签名、exe RVA） | **证据不足** | 目标由签名扫描运行时解析，静态 asi 不存 exe RVA；handler 与游戏原型的 `ECX=this` / 浮点返回 / 栈清理逐项未对照 |
| 命中后译文缓冲的输出编码（UTF-8 直拷 vs 二次转 UTF-16） | **证据不足** | 命中路径 `0x1E876` 为 memcpy；输出缓冲最终编码需结合下游 `0xBAD0` / `0xBBF0` 与动态快照确认 |

**中文替换发生在哪一步：** 替换点在**排版 / 宽度计算 / 字形绘制之前的取串（串包装）层**——`0xB6A0` / `0xB3C0` 在源串进入宽度函数 `0x6210`、单字宽 `0x5F70`、绘制 `0x6660` 之前完成哈希查表与译文回填；下游的 `0xBAD0`（UTF-16→UTF-8）、`0xBBF0`（UTF-16→ANSI 逐字）、`0x1FCE0`（格式符解析）是编码 / 格式转换层，宽度与绘制层（`0x6210` / `0x6120` / `0x5F70` / `0x6660` / `0x6620`）负责度量与上屏。未命中的串以原文透传到这些下游层。

**与首版口径的差异：** §5.1 / §7 把「key→string 查询层是否被 hook」列为未确定；本轮反汇编已在 asi 侧确认存在被安装的哈希查表取串 handler。需注意边界：被接管的是 asi 挂接的取串 / 包装入口，**不是** exe 内部 GXT key→string 查询函数；剧情长文本的取串仍走游戏自带 GXT 链路（9.3 第二段）。

### 9.5 本轮新增 / 修正的事实清单

1. 版本串 `0x10027DE0` 仅为记录表标注，无运行时版本 / 大小 / 哈希比较；`01` 无校验结论成立，首版「版本锁」措辞作废。
2. `0x8620` 为 `.text` 机器码签名唯一命中后的 9 字节代码补丁；失配静默 `ret`（出口 `0x87B2`），不写日志不弹窗。
3. 57 / 3 是 asi 侧安装器调用点数；exe 目标 RVA 运行时由签名解析回填，静态不可列；E8 压返回地址、E9 不压；回跳经 `DAT_10037B20/B24` 与桩 `0x77D0`。
4. 短串查表算法为 **FNV-1a 32**（basis `0x811C9DC5`、prime `0x01000193`）+ 附加 finalization 与全局 salt `0x10037A28`；查表 handler `0xB6A0` / `0xB3C0`，桶链查询 `0xA560`，透传拷贝 `0xA330`。
5. 两段式判定成立：短串 asi 侧哈希换中文（未命中透传英文）；剧情长文本走外部替换 gxt 的游戏自带链路，asi 不接管 GXT。
6. 查询层三态：asi 取串包装入口被 hook（已证实）；exe GXT 解析函数未被引用（已排除）；exe 原型 / RVA 与译文输出编码（证据不足），需动态快照补证。
