## 坑 1（2026-11-08 重大）apply_zh.py 的输出被管道截断，TBoGT 章静默不执行

**症状**：三章 gxt 连续两版字节数完全相同（`2,658,052 / 776,386 / 966,802`），`gxt_verify_engine` 却报 OVERALL PASS、六处哈希全 True。

**根因**：`apply_zh.py` 的 `__main__` 是三章循环：

```python
for c in CH:      # CH = ["base", "TLAD", "TBoGT"]
    apply(c)
```

每章结尾都会 `print(...)`。命令里用了 `| Select-Object -First 1` 取第一行，**PowerShell 在拿到第一条输出后就关闭管道**，Python 下一次 `print` 抛 `OSError Errno 22`，循环死在 base 之后 —— TLAD/TBoGT 的 `src_*_tr.tsv` 根本没重写。

**为什么难发现**：`gxt_verify_engine` 比对的是「src 与 gxt 是否一致」，src 没更新时两边自然一致，PASS 是真话但没意义；哈希比对只证明「部署的和 build 里的一样」。**这两个闸门都不检查「覆盖表的改动有没有进 tr 表」**。

**规程**：
- 跑 `apply_zh.py`、`gxt_pack.py`、`gxt_verify_engine.py` **一律重定向到文件再整份读**，禁止接 `Select-Object -First N` / `-Last N` 截断。
  ```powershell
  python -X utf8 "C:\Game\_tools\apply_zh.py" > "$env:TEMP\applylog.txt" 2>&1
  Get-Content "$env:TEMP\applylog.txt"
  ```
- 打包后必须确认 **三章的「应用 N 条译文」都打印出来**（正常值：base 3307 / TLAD 957 / TBoGT 729 左右）。
- 部署后必须做一次**内容抽样**，不能只看哈希：从部署的 gxt 里按 crc 取一条刚改的译文。
  ```powershell
  python -X utf8 "C:\Game\_tools\_tmp_checkgxt.py"
  ```
  该脚本用 `gxt_extract.parse_gxt`（返回 `(tables, entries)`，**entries 是三元组 `(name, crc, txt)`**），命中数必须等于抽样数。
- 判据：只要本次改动落在 TBoGT 章，`zchs_TBoGT_tr.gxt` 字节数**必须变化**；落在 TLAD 章则 `zchs_TLAD_tr.gxt` 变；base 同理。三章全不变 + 有改动要落 → 一定是流程断了，不是「刚好长度相同」。

## 坑 2 长条目的 zh_old 不能从 dump 行取

`dumpline5.py` 输出的 E/Z 都是截断的（E 85 字、Z 95 字）。拿 dump 当 `zh_old` 落表会写进半截文本，`qa_gate` 报控制符不匹配（典型：`原文['~n~','~n~'] 译文['~n~']`）。

**规程**：落表前按 crc 去 `data\corpus_*.tsv` 的 `chinese_current` 取完整值，`repr()` 确认 `~z~`/`~n~`/`~a~`/`~1~` 齐全。

**更稳的写法（已内置于本轮全部 `_tmp_log_*.py`）**：先查覆盖表，没有才回落母本 ——

```python
src = cur.get((crc, CH)) or corpus.get((crc, CH), ("", "", ""))[2]
```

因为该条一旦已在覆盖表里，`corpus` 的 `chinese_current` 就是**旧值**，拿它当 `zh_old` 会匹配不上（或被二次改写）。

## 坑 6 德法不是永远可靠的同句证人（拍板 3A）

**背景**：`TBoGT|E2CM1AU`（喜剧俱乐部单口段，269 条）里同一 crc 的英语与德语不是同一句。核查官方 gxt 结论：

```
官方 TBoGT   american=269  german=256  french=256
德语/法语：空文本 0 条，crc 不存在 13 条   ← 官方本地化本身就少 13 条
```

且德语的**排列也与英语不同**（`2F9F51A6` 英语 `Can I ask you something, pal` 的德语位装的是「当你六十岁」，而那句在英语里属于 `4B938AAE`）。所以不是我们语料构建丢失，也不是单纯合并。

**规程（全局规则，所有表通用）**：

1. 逐条读时先看德法与英语是否同句。若明显不同句，该条标为「不可对照」。
2. 该条**只依英语判中文对错**，德法不得作证人 —— 强当证人会拿错句比，制造假阳性。
3. 德法仍可作**整段语境参考**（判断这段在讲什么），只是不能逐句对应。
4. 同时留意**中文是否贴着德文译**：若某条中文语义明显贴德文而不贴英文，就是上游串译，必须改。

**已确认高风险表**（空率 ≥4%，德法大概率不对齐，读到即按上述规则）：

`TLAD|E1J1AUD`(7.6%)、`base|GM3CAUD`(14.3%)、`TLAD|E1MF3AU`(5.0%)、`TBoGT|BUSSTOP`(72.7%)、`TBoGT|E2CM1AU`(4.8%)、`TLAD|E1R2AUD`(4.0%)、`TBoGT|DANCING`(20.0%)、`base|PUZZLE`(11.1%)

全清单见 `docs\三语对照可靠性-普查清单.md`。

**已被推翻的判据（别重复试）**：

- ❌ 「E 与 D 标点签名不一致」判错位 —— 方向反了，`D=F≠E` 是表健康的信号
- ❌ 「D/F 长度比极端」判错位 —— 三语天然长度差大，抓不到真问题
- ❌ 「专名 Jaccard 低」判错位 —— 无人名的表天然为 0，那是「无法判定」不是「错位」
- ✅ 可靠信号：同表内德法成对为空、k=0 不是最优位移

## 坑 7（本段实际事故）替换的 new 片段复用了 old 片段里的词，拼接出重复文句

**症状**：`6DB05035` 落表后 `zh_new` 变成「这架金色的怪兽**这架金色怪兽里**我是躲不了」。

**成因**：`old` 片段与 `new` 片段在脚本里各自独立书写，`new` 里又抄了一遍 `old` 中的词，`str.replace` 之后自然是「old 剩余部分 + new 全文」拼接。

**规程**：
- **落表的 new 片段不允许包含 old 片段中已出现的连续词块**（除有意保留的专名）。
- 每条落表后**必须回读 `zh_new` 逐一目视**，不能只看「待落表 N / N 全部命中」。
- 单条二次修正的模板见 `C:\Game\_tools\_tmp_log_d2b.py`（同 crc 再落一条，日志条数 +1，覆盖表行数不变）。

## 坑 8 `qa_gate` 警告数突然 +N 先判「是新问题还是暴露了既有问题」

本段 `31C74E52` 落表后警告从 28 变 29。原因是该条**本身带上游多余的 `~n~`**，它进入覆盖表后才第一次被闸门检查到 —— 属**既有问题被新条目暴露**，不是本次改动引入的新缺陷。

**规程**：
1. 先看新增警告的 crc 与文本，判断属于哪一类。
2. 若属拍板 B3 三项（控制符顺序不符 / 上游多余 `~n~` / 多余 `~s~`），**保持现状不清理**。
3. 只有确实是本次改动引入的（比如我方删漏了控制符、标点半角化），才回头改。

## 坑 9 长条目中间夹 `~n~` 时整段 old 匹配失败

**症状**：脚本报 `!! 片段不存在`，但人工看着文本「明明一样」。

**成因**：`~n~` 前后可能有上游的空格/控制符差异，整段长串一点不匹配就全失败。

**规程**：
- 退化成**单片段替换**：只圈住要改的那半句，避开 `~n~` 边界。
- 同一 crc 需要多条 FIX 时，用 `work` 字典承接上一次结果，逐次 `work[crc] = work[crc].replace(...)`，最后一次统一写入。模板见 `_tmp_log_b5.py`。
- 带 `~z~` / `~x~` / `~s~` 前缀的条目，`zh_old` **必须连前缀一起写**。

## 坑 10 `\xNN` 类脏字符一律先判断原字符再替换，**不要直接删**

**背景**：`SIXAXIS™` 里的 `™` 被前批清理当成脏字符删掉了，造成 23 条丢失商标符。这批已于 2026-11-08 全部补回。

**脏字符的真实身份**（UTF-8 被按 cp1252 解码的残留）：

| 字节 | 真实字符 |
|---|---|
| `\x93` / `\x94` | `“` / `”`（U+201C / U+201D） |
| `\x92` | `’`（U+2019） |
| `\x99` | `™`（U+2122） |

**规程**：
1. 先 `repr()` 看上下文，判断这个字节本该是什么字符。
2. **能还原就还原**（`\x99`→`™`、`\x93\x94`→`“”`），不要图省事删掉。
3. 人名/店名引号已规范成 `「」` 的，**不要动**（`E8506E8D` 的 `<a href=...>` 曾被删引号，要补回合法 HTML）。

**扫错表的坑**：脏字符扫描要扫**覆盖表 `zh_global.tsv`**（生效值），不是 `corpus_*.tsv`（母本）。扫母本会永远报 34 条，看着像没修好，其实覆盖表早就接管了。

## 坑 13 网络梗禁用表曾自设并滥用，已整张作废（判据改回「原文语义」）

2026-11-08 用户拍板作废。原 23 项网络梗/粤语清单 + 自加的「卧龙」不再作为判据。

**踩过的三个坑**：

1. **来历不明**：表只存在于建档时的转述，拿不出用户原话。**来源不可追溯的规则，不该当硬标准执行。**
2. **越界扩张**：表里「逼作侮辱后缀」被扩成「净化一切侮辱词」，与用户拍板「侮辱词口径不用动」正面冲突，曾批量 `狗逼/傻逼/贱逼 → 混蛋/蠢货/白痴/孙子`（40+ 条，35 条后来被覆盖回原样）。
3. **误判正常中文**：`prestigious award` 的「重量级奖项」、`I'll buy next time` 的「下次一定买」都是正常中文，被当成网络梗改掉。

**现行判据**：只看**原文语义是否到位**——原文有脏话/俚语/程度副词必须译出，原文没有的不许自加，侮辱词不做净化。

**本类改动特有的隐蔽坑（比规则本身更值得记）**：这类改动会大量「假生效」——日志记了改动，但后来用 `corpus` 的 `chinese_current` 当 `zh_old` 重写时把它冲掉，源表仍是原样。
**核对方法**：拿日志的 `zh_new` 与源表**当前值**逐条比对，不能相信「日志写过就算改过」。本次 82 条中有 35 条属于此列（`_tmp_banned_audit.py`）。

## 坑：zh_global.tsv 被写成带 BOM → qa 全表判空

- 现象：某批落表后 `qa_gate.py` 的「合计：检查 N 条」从 8,938 骤降到 1,803，错误/警告仍是 0，看起来像「质量变好了」，实际是**大部分条目没被检查**。
- 根因：`qa_gate.py` 第 80 行用 `encoding="utf-8"` 读 `zh_global.tsv`；一旦文件带 UTF-8 BOM，首字段名变成 `﻿crc`，`r.get("crc")` 恒为 None → 第 84 行 `if not c ... continue` 把整表跳过，只剩 `zh_<chapter>_*.tsv` 分片补全的那部分。
- 硬约束：**`zh_global.tsv` 必须无 BOM**（实测原文件 `raw[:3] != b"ï»¿"`）。审读日志则**带 BOM**，两者相反，别一视同仁。
- 回写模板（保住无 BOM）：`txt = open(p,"rb").read().decode("utf-8-sig"); open(p,"wb").write(txt.encode("utf-8"))`。不要用 `open(p,"w",encoding="utf-8-sig")` 写 `zh_global.tsv`。

## 坑：fixes 5 列 tsv 少一个 tab → 整批不落表但断点照常推进

- 现象：`append_log.py` 报 `ValueError: not enough values to unpack (expected 5, got 4)`，紧接着 `patch_polish1.py` 报「新增 0」，`qa_gate` 条数不变；但 `pass_state.py --offset` 已经把断点推到了新值 —— **数据没进、断点走了**，这是最危险的一种错。
- 成因：某行「新译正文」和「理由」之间漏了 tab，两段黏成一列。
- 规矩：每批落表后**必须核对**「覆盖表行数增量 == fixes 行数」，不等就立刻查；`append_log` 末行的「新增 k」也要跟 fixes 行数对上。

## 坑：队列 english 带 `~z~~c~` 前缀的条目会静默漏落

- 现象：某条在 `上游润色_队列.tsv` 里存在、在 `zh_global.tsv` 里**没有基行**，`append_log` 关联不到 english 就写成空 english；`patch_polish1` 按 `(crc, chapter)` 找不到、按 english 反查也找不到 → 该条不落表，其余条目正常。表现为「12 条 fixes，覆盖表只 +11」。
- 定位：按 `crc` 逐条核对 `zh_global.tsv` 是否存在。
- 补法：往 `zh_global.tsv` 追加一行 `crc / zh / chapter / english / was`（english 用队列里的带前缀原文），再往日志补一行同 `crc` 的审读记录。补完必须重跑 `qa_gate` 确认条数 +1 且错误为 0。

## 坑：用 csv.DictReader 数行数会把 src_*_tr.tsv / zh_global.tsv 数少（误报丢行）

- 现象：`apply_zh.py` 打印「base: 应用 N 条译文，共 59661 行」，但用 `csv.DictReader` 数 `src_base_tr.tsv` 只得 50,140 行，看起来像少了 9,521 条。曾一度被判为「apply_zh 丢行」。
- 真因：这些 tsv 里有文本字段含引号，`csv` 解析器会把跨行字段**合并成一条记录**，于是记录数少于物理行数。数据其实完整。
- 核对行数必须数物理换行：`raw = open(p,"rb").read(); raw.count(b"\n")`。表头占 1 行，故 `物理行数 - 1` 才是条目数。
- 本仓已复核（p10865）：`src_base.tsv` 59,662 / `src_base_tr.tsv` 59,662 / `src_TLAD_tr.tsv` 18,558 / `src_TBoGT_tr.tsv` 23,912（均含表头），条目数与 gxt 打包回读的 59,661 / 18,557 / 23,911 完全吻合。


## 坑五：只删覆盖表行不够，日志残留会让 patch_polish1 把它重放回来

**症状**：某条译文判定要回退（例如占位符 `DIALOGUE MISSING` 保持英文会触发 qa `[未译]`），手动从 `zh_global.tsv` 删掉该行后 qa 归零；但下一批跑完 `patch_polish1`，该条又出现在覆盖表里，qa 重新报 1 错。

**真因**：`patch_polish1` 每次运行都会**全量重放**审读日志，日志里留着这条记录，就等于每次重建它。

**正确做法**：回退一条已落表的译文必须**两处一起删**——
1. `zh_global.tsv` 删该 crc 行；
2. `上游润色_审读日志.tsv` 删该 crc 对应的日志行。
只做第 1 步 = 下一批自动复活。

**另一个陷阱**：删日志行不能用 `split("\n")` + `join` 重写整个文件。日志字段里有含换行的译文，物理行 ≠ csv 记录，那样会把一条记录拆成几条。本坑实测一度造成 qa 报 113 错（一度误判为数据被拆坏，其实不是）。只删目标行时按"整行前缀匹配 `crc`"过滤即可，不要动其它行。

## 坑六：`fix_ctrl` 之后跑 `patch_polish1` = 112 行控制符被冲回，qa 直接报 113 错

**症状**：qa 突然报 113 错（此前是 0），且错误形态与"补控制符 112 行"那次一模一样。

**真因**：`patch_polish1` 按日志把 `zh_old`→覆盖表，会把 `fix_ctrl` 刚补齐的控制符覆盖掉。113 = 112 条控制符 + 1 条真实未译。

**正确顺序（不可颠倒）**：`append_log` → `patch_polish1` → `fix_ctrl` → `qa_gate`。
若因回退/补录不得不重跑 `patch_polish1`，必须紧接着再跑一次 `fix_ctrl` 才能跑 qa。

## 坑：fixes 的「新译正文」不能以颜色标签开头（P1 段实证，一次 10 条）

`fix_ctrl.py` 会按**原文**自动补开头颜色标签。若 fixes 里自己写了 `~z~~x~正文`，
`fix_ctrl` 会再补一层，得到 `~z~~x~~z~~x~正文`，`qa_gate` 报 `E [控制符]`。

**纪律**：fixes 第 4 列只写正文，开头标签一律交给 `fix_ctrl`。

**事后修法**：不要重交 fixes（会命中「已同」跳过）。写纯文本 split/join 脚本，
同时改 `zh_global.tsv` 第 1 列与日志 `p[5]`（**crc 在 `p[2]`**，`p[0]` 是 chapter），
先 `shutil.copy2` 备份，`newline="\n"`。参考 `build\tmp_q\_tmp_fixdup.py`。
禁止用 csv 模块整表重写。

## 坑：`~s~` / `~1~` 标签位置与顺序不能自造（`1084AEED`）

原文 `~s~Go to SoBoHoe's by ~1~:~1~.`（标签 `['~1~','~1~','~s~']`）。
手写 `~s~~1~~s~~1~:~1~ 前到 SoBoHoe 家。` 会让译文标签数多于原文，
`fix_ctrl` 再补一个 `~s~` 后 `qa_gate` 报 `E [控制符]`。

**纪律**：译文只写 `~1~:~1~ 前到 SoBoHoe 家。`，让 `fix_ctrl` 按原文补 1 个 `~s~`。
标签严格按原文的**数量与位置**还原，不调整顺序、不合并、不拆分。

## 坑 44：fixes 正文不能以颜色标签开头（P2 段复现）

写 fixes 时若把原文开头的 `~z~~x~` 原样带到「新译正文」里，`fix_ctrl` 会再补一层，触发 `E [控制符]`。

- `safe_append.py` 打印的「剥离 N 处开头重复标签」只处理**重复**标签（`~z~~z~`），**不处理单层**。
- 正确做法：新译正文只写纯文本，开头标签交给 `fix_ctrl` 按原文补；落表前用一段字符串 replace 自查一遍。
- 本段 `0301` 批（`268103EA` / `269D16C4` / `2C97F610`）就是先踩再当场剥掉的。

## 坑 45：按键名并置必须补「和 / 或」，但不得增删标签

原文 `Use ~PAD_LEFT~ and ~PAD_RIGHT~ to browse shoes.` 逐字直译成 `用~PAD_LEFT~~PAD_RIGHT~浏览鞋子` 后，中文读不成句（两个标签直接贴在一起）。

- 判据：英文里用 `and` / `or` / `+` 连接两个键名，中文对应位置就要有「和」/「或」。
- 但补的是**连接词**，不是标签：标签数量、顺序、颜色码一律照原文，不许加 `~s~` 分隔。
- 同类还有 `~INPUT_VEH_EXIT~/~INPUT_PICKUP~` 后面 `leave X` 的宾语（「不买鞋离开」），漏了宾语就成了「离开」。

## 坑 46：`skip` 的宾语是「这段行程」

带司机 / 出租车的 UI 文案里 `Press ACCEPT to skip` / `to skip at extra cost` 指的是**跳过这段路上行程**，不是跳过动画。本段一次性修了 8 条「跳过动画」（`83A2478B`、`A6FD0E40`、`5950208D`、`115F90AD`、`4BFC85E6` 等）。

- 同一批里 `holding ~X~` 与 `pressing ~X~` 也要分开译「长按 / 按」，原译一律写成「长按」（`B8D3F4D5` 对照 `04B93AC0`）。


## 坑 47：导出预览的「截断」不一定是原文截断

挂起表里三条被判「原文被截断」的条目（`E50E2243`、`BBC92791`、`1AEDA761`），逐一回读后发现：

- `E50E2243` / `BBC92791`：**原文是完整的**，只是导出预览按字数截断（`...dragged through the fuc[---]`、`and an occasional...`）。
- `1AEDA761`：`When a book is called "Guns,` —— **原文真的就在书名中途断句**（引号未闭合，下一条接书名后半）。

判据与做法：
- 别相信预览行的 `[---]（原文截断）` 标注，直接读 `上游润色_队列.tsv` 的 `english` 列（该列是完整字段），或 `parse_gxt` 读三章原版 `american.gxt`。
- 原文真断句时，译文要在**同一个断点**断开，并保留未闭合的引号形态；不要替它补全书名。

## 坑 48：覆盖表里 chapter 为空的行对三章都生效，且同 crc 是「后行覆盖前行」

`apply_zh.load_global` 的判定是 `if c and z and (not ch or ch == chapter)`，并且 `out[c] = z` 逐行赋值。

后果两条：
1. **chapter 为空的行对所有章生效**——一个想只在 base 生效的译名，会顺带作用到 TLAD / TBoGT。
2. **同 crc 出现两行时，文件里靠后的那行生效**——新写入的行追加在尾部，所以「新行」会赢；但如果手工调序或删行，胜负会反转。

本次踩到的具体事故：`fixes` 按 `chapter=TLAD` 写入 `446D60CD` 后，表里原有的空 chapter 旧行（`擀面杖…*`）依然在，形成同 crc 重复。已删 5 行重复旧行解决。

处置原则：
- 写入前先 grep 该 crc 是否已有空 chapter 行；有就**同时删旧行**，不要只加新行。
- 存量仍有 2,209 行空 chapter / 约 145 个重复 crc，属早期遗留；批量补 chapter 有把「跨章通用译名」误锁进单章的风险，需先拍板再动。

## 坑 49：三语平行官方译本是判歧义原文的硬证据

`Go. Roll the bitch!` 一条，英语里 roll 歧义极大（滚动 / 开拍 / 开音响 / 开车）。查同 crc 的意/法/西三语官方译文：`Pompa il volume` / `Fais péter le son` / `Dale caña` —— 三者一致指向「把音响放起来」，据此定案「去。把音响轰起来！」

`E mio.` 同理：意/法原文都保留 `E mio`（意大利语），西语官方译作 `Soy yo`（是我）→ 现译「是我。」正确，可以结案不改。

做法：`parse_gxt` 读同目录的 `american.gxt` / `french.gxt` / `german.gxt` / `italian.gxt` / `spanish.gxt`，按同一 crc 取同表同键对比。判歧义优先信三个独立译者的一致理解，其次信词典义。

## 坑 50：中文省略号 `…` 会被 CHAR_MAP 转成三个半角点

`apply_zh.CHAR_MAP` 把 `U+2026 …` 映射成 `...`（ASCII 三点，因为 `…` 不在图集内）。所以写「那个……」进表后，游戏里显示的是「那个......」。

- 需要停顿语气时用「呃，」「，」等替代，不要靠省略号。
- 注意 `CHAR_MAP` 同时把 `·`→`･`、`（）`→`()`、`“”`→`「」`；写 fixes 时按最终显示形态想一遍。
